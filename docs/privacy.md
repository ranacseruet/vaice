# Privacy

- `~/.vaice/conversation.json` is written with mode **0600** (owner read/write only) via a temporary file and `os.replace`, so a reader never sees a half-written file; the `~/.vaice` directory itself is created with the usual 0755 permissions, meaning other local users can see that the file exists (not what it holds).
- The transcript is retained **indefinitely**, until you click **New conversation** (which clears it) or delete the file while `vaice` is stopped. New conversation is the way to forget everything, including any embarrassing questions.
- By default `vaice` talks to one server: the `llama-server` at `VAICE_LLAMACPP_URL` (local by default, e.g. `http://localhost:8001`) over HTTP and WebSocket. The microphone audio, the transcripts, the skill results and the model's replies go there; nothing else leaves the machine through `vaice` itself except one startup request to `huggingface.co` (the next bullet). The exceptions are opt-in and listed below: the [vision skill](screen-vision.md)'s screenshot, [MCP tools](mcp-tools.md) and [browser tasks](browser-tasks.md). The skills run in vaice with *vaice's* permissions (llama-server's own tools are not used), and with `VAICE_SHELL` on that includes any shell command you approve with the Run button, with the same access to your files as you have, and its output goes to the model and into the conversation file. If you point `VAICE_LLAMACPP_URL` at a remote host, your audio and conversation go there instead.
- Gradio, the UI library `vaice` runs on, sends usage telemetry (through `huggingface.co`) and checks `api.gradio.app` for a newer version at every start. `vaice` turns that off by setting `GRADIO_ANALYTICS_ENABLED=False` before the UI is built ([#98](https://github.com/ranacseruet/vaice/issues/98)); set `GRADIO_ANALYTICS_ENABLED=True` in the environment or the `.env` to turn it back on (a value you set is never overridden). What still goes out at startup is one `HEAD` request to `huggingface.co` that checks the Silero voice-activity model (`silero_vad.onnx`, used by fastrtc) for a newer revision. The model is downloaded once, on the first start, into the Hugging Face cache (`~/.cache/huggingface`) and used from there afterwards; the request carries no audio or conversation. Once the model is cached, `HF_HUB_OFFLINE=1` stops that request too (without a cached copy the model cannot be loaded); turning it off by default is [#143](https://github.com/ranacseruet/vaice/issues/143).
- With the [vision skill](screen-vision.md) on (`VAICE_VISION_URL`), a screenshot of your **main display** is taken **only when the skill runs** (you asked about your screen), sent to the vision endpoint with your question, and deleted from this Mac right after (a private temporary file, never stored by vaice, never logged). The screen can show anything: mail, messages, passwords in a visible window. If the endpoint is on another machine or a hosted API, that image leaves your machine (startup warns). The vision model's answer is stored in the conversation file like any skill result (up to 800 characters in the *Tool activity* record).
- With [MCP tools](mcp-tools.md) on (`VAICE_MCP_CONFIG`), vaice starts the servers you list as programs with **your** permissions and the `env` you give them, and the arguments the model chooses (from what you said) go to them. A tool's result reaches the model, is stored in the conversation file like any skill result (up to 800 characters in the *Tool activity* record). What a server does with your data is up to that server (an `npx` or `uvx` package fetches and runs code), so list only servers you trust. The `env` values in the file are never logged; the file itself is plain text, so keep it private.
- With [browser tasks](browser-tasks.md) on (`VAICE_BROWSE=pi` or `acp`), the browser agent opens pages in a Chrome window with a profile of its own under `~/.vaice/browse/` (cookies and logins persist there, in plain files Chrome keeps; delete the directory while `vaice` is stopped to forget them). Your goal and what the pages show go to the **agent's model endpoint**: with `pi` the `VAICE_BROWSE_URL` host (Pi's own model; startup warns) and the key (`VAICE_BROWSE_API_KEY`) only through Pi's environment, which holds nothing else of vaice's; with `acp` whatever endpoint the agent is configured for (vaice does not know it), and the agent starts with your environment minus every `VAICE_*` variable, so your own provider keys are visible to it. vaice only gates what the agent asks about: its own tools and permission mode are set in its config. The agent can open any site; a step that changes a page needs your click on Run. The task's spoken lines (its start, each step's heads-up, [#127](https://github.com/ranacseruet/vaice/issues/127), and the outcome) are stored in the conversation file with the turn that asked, and so is the agent's whole answer (up to 12000 characters, shown in the chat); the pages themselves are not. The last ended task's goal, outcome and answer are also kept **in memory only** so that "what did you find?" can be answered (until a new task, *New conversation* or the app stops). While a finished task is kept, its goal and the agent's one-line `Summary:` (cleaned, capped at 400 characters; nothing else of the answer) are also part of the prompt of every reply, so they go to the local `llama-server` like the rest of the conversation.
- The notes you ask the assistant to remember are kept in `~/.vaice/memory.json` (mode **0600**, same atomic write), **indefinitely**, and are not cleared by *New conversation*: say "forget everything", delete the file while `vaice` is stopped, or turn `VAICE_MEMORY` off (the default; then the file is neither read nor written). Every reply's prompt carries the notes, which go to the local `llama-server` like the rest of the conversation.
- Set `VAICE_DATA_DIR=""` to keep the conversation and the notes **in memory only**: nothing is read from or written to disk, and history disappears when the app stops. Persistence can also be limited with `VAICE_HISTORY_TURNS` (the prompt window), which trims context but keeps the file — set `VAICE_DATA_DIR=""` if the file itself is the concern.
