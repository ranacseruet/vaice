# AGENTS.md

This file provides guidance to coding agents (Claude Code, Codex, Cursor, …) when working with code in this repository. Claude Code reads it through the `@AGENTS.md` import in `CLAUDE.md`.

## What this is

`vaice` is a single-user voice demo: browser mic → fastrtc (WebRTC + VAD) → a `Responder` → spoken reply streamed back, with a persisted multi-turn conversation. The default `llamacpp` responder sends audio to llama.cpp `llama-server` (LFM3-Audio, `/v1/realtime` WebSocket). The explicit `text` responder runs sherpa-onnx Whisper and Kokoro locally around an OpenAI-compatible streaming chat endpoint. Python 3.10–3.12 are the CI-tested versions; CI runs on macOS, and other OS audio behavior is not validated. See `README.md` for the user-facing description and the env-var table.

## Commands

```bash
uv venv .venv && uv pip install -e ".[dev]"               # setup, default realtime path
uv pip install -e ".[dev,local-voice]"                    # optional text pipeline dependency
.venv/bin/pytest                               # all tests
.venv/bin/pytest tests/test_llamacpp.py -k history      # single test
.venv/bin/vaice                                   # run; UI at http://127.0.0.1:7860
```

Ruff is configured (`pyproject.toml`: line length 120, lint rules in `[tool.ruff.lint]`); it is not a formatter, so no formatting step. Unit tests use fakes for the servers and model responses. The sherpa-onnx Whisper Tiny and Kokoro APIs were smoke-tested against real official model assets; there is no automated test against real models or the browser mic. Verify the end-to-end audio path by hand with a compatible server.

## Architecture

`app.py` wraps a `Responder` (`responders/base.py`: `respond(audio, history, turn) -> Iterator[(sample_rate, float32 samples)]`) in a fastrtc `ReplyOnPause` handler, logs time to first audio, and shows the conversation in a Gradio chatbot with a "New conversation" button. `VAICE_PIPELINE` defaults to `realtime`; startup checks the model's known modalities and accepts the configured realtime path. `auto` requires advertised audio input and output plus a successful `/v1/realtime` handshake; unknown metadata stays unknown, and text mode is explicit because modality metadata does not prove chat-completions support. An unreachable/loading llama-server warns and the UI still starts. The page heading and subtitle come from fastrtc's `ui_args`; the chatbot is 500 px tall and sets `allow_tags=False`, because Gradio 6.0 flips that default to `True` and would render the model's text as HTML. Clicking "New conversation" clears the stored conversation and silences the reply in flight; what you say after the click is the new conversation's first turn, with no earlier turns in the prompt. A 1 s `gr.Timer` re-pushes the chatbot view when it changed (views are deduplicated as JSON), so a transcript that lands after the reply's final update still replaces the "…". `conversation.py` owns history: `Conversation.start_turn()` closes the previous turn (unfinished = interrupted), `history()` gives the windowed text turns (a turn whose transcript has not arrived yet is dropped from the prompt, so the model never sees a reply to an unreadable question), and everything is saved to `~/.vaice/conversation.json`. Responders report the transcript exactly once (even on failure) and the cumulative text covered by audio handed out on `Turn`; `app.py` reports the audio seconds handed out, which `Turn.close()` uses to estimate what played.

- **`LlamaCppResponder`** (`responders/llamacpp.py`): per reply, a fresh `/v1/realtime` session on a daemon thread of its own (`_converse`): `session.update` (instructions = mode line + prompt + the earlier turns as `User:`/`Assistant:` text, `output_modalities` text+audio, `max_output_tokens` 512), the whole utterance as one `input_audio_buffer.append` (mic audio resampled to the session's input rate), `response.create`; `response.output_audio.delta` frames come back through a queue, the text deltas feed `Turn.set_assistant_text` (split by the share of audio, `base.spoken_part`). A second `transcription` session on its own daemon thread (`_transcribe_into`) reports the user's transcript exactly once. Closing the socket cancels the reply on the server.
- **`TextResponder`** (`responders/text.py`): first transcribes with lazy, in-process sherpa-onnx Whisper Tiny; it sends history and the transcript to `/chat/completions` at `VAICE_TEXT_URL`, buffers streamed text until a complete sentence, and uses lazy sherpa-onnx Kokoro to synthesize it. Model inference and HTTP streaming run on a dedicated daemon worker, not fastrtc's thread-per-resume generator. Audio queue events carry their sentence/sample coverage so later TTS work cannot make unhanded text appear spoken. Cancellation closes the HTTP response on a helper daemon thread so a blocked close cannot hold fastrtc or process shutdown. The optional `local-voice` extra is separate from the default dependencies.
- **Stopping:** `lifecycle.py` holds the app's stop signal. `app.py:main()` installs the SIGINT handler before checking the server, so Ctrl+C sets the flag and gradio closes the server; the llamacpp session threads are daemons, so a server that never answers or never completes the websocket upgrade cannot keep the process alive. The generator only polls a queue, so it notices the stop signal within `POLL_SECONDS` even while `connect()` hangs.

Config is env-driven in `config.py` (`VAICE_*`). `--backend` and `VAICE_BACKEND` are removed; startup rejects a set `VAICE_BACKEND` with migration guidance.

## Gotchas (each has bitten this repo)

- **fastrtc threading:** fastrtc resumes the reply generator on a different worker thread for each chunk. When testing code that runs inside a framework executor, reproduce this real threading (fresh thread per resume) and confirm the test fails against known-bad code first; a harness that called `emit()` from one thread passed while the live app failed.
- **The stop signal:** gradio installs no SIGINT handler of its own (`gradio/http_server.py:47 install_signal_handlers` is `pass`; its uvicorn server runs in a daemon thread and `uvicorn/server.py:332 capture_signals` only listens on the main thread), so `lifecycle.py:install_stop_handler()` stays in charge: Ctrl+C sets `lifecycle.stopping` and raises `KeyboardInterrupt`, which gradio's `block_thread` (`gradio/blocks.py:3044`) turns into `server.close()`. The responder polls the flag while it waits for the server and returns without a reply.
- **fastrtc's idle polling:** `player_worker_decode` (`utils.py`) loops `await loop.run_in_executor(None, handler.emit)` as fast as the executor can schedule it, so an idle connection burned ~64% of a core (~32k `emit()` calls/s, measured). `InterruptSafeReplyOnPause.emit()` waits for the pause event (`self.event.wait(timeout=IDLE_WAIT_SECONDS)`) instead of returning None at once: ~37 calls/s, ~1% of a core. The wait ends as soon as the event is set, so no latency is added — and `emit()` runs in a worker thread (the asyncio default executor in the WebRTC path, an anyio worker thread in the websocket path), never on the event loop.
- **Single connection:** fastrtc's `Stream` defaults to `concurrency_limit=1`, so a second WebRTC connection is refused (`concurrency_limit_reached`), not queued. A page reload is not affected (Chrome closes the old peer connection on navigation, so the slot is free within ms; measured), but a connection the browser never closes (tab force-closed, browser closed, measured headless via Playwright) holds the slot ~30 s until aioice's consent checks expire (6 failures x ~5 s). The reload console errors `BodyStreamBuffer was aborted` / `Connection errored out` come from Gradio's JS client when the navigation cuts its open `queue/data` event stream (the only request in flight at reload); harmless, and never seen without the chatbot/`additional_outputs`. Barge-in: fastrtc's `close()` on the reply generator fails ("generator already executing") because `emit()` is mid-`next()` on another thread; the reply actually stops when CPython finalizes the dropped generator. The `next()` that was in flight still returns a chunk, which fastrtc would queue after clearing and play; `interruptible.py:InterruptSafeReplyOnPause` (what `app.py` uses) drops it by noticing that `receive()` replaced `self.generator` while `emit()` ran. It relies on fastrtc 0.0.34 internals (`generator` is set to None on interrupt; `copy()` must be overridden because fastrtc copies the handler per connection — `interruptible.py:copy()` passes every argument by keyword and `_copy_kwargs()` is checked against `ReplyOnPause.__init__`'s signature in `tests/test_interruptible.py`, so a fastrtc release that adds, drops or reorders a parameter fails there instead of silently misplacing a value), and `tests/test_interruptible.py` drives the real `ReplyOnPause` so a fastrtc upgrade that changes this fails there. A chunk handed to fastrtc just before the interrupt still plays. Replies are capped at 512 tokens (text + audio frames); truncation is logged. On barge-in (fastrtc acts when the interrupting utterance *ends*), the next `start_turn()` freezes the old turn, so a late finalization can't change history, and cuts its text to the share of audio that could have played since the first chunk (handed out ≠ played: fastrtc's playback queue is unbounded). LFM's interleaved text runs ~2x ahead of its audio, so the text is split by the share of audio generated (`base.spoken_part`).
- **llama-server realtime: history is text in `instructions`, one fresh session per reply:** `conversation.item.create` with the assistant role is rejected ("only user messages and function call outputs are supported"), so earlier turns can't be replayed as items. A fresh session per reply with the history in `instructions` (set before the first audio/message) is honoured by LFM3-Audio and keeps `conversation.py` the single owner of history (windowing, barge-in cuts, "New conversation").
- **llama-server realtime: no user transcript in a conversation session:** the transcript comes from a second session (`session.update` type `transcription`, no language so the model detects it: `common/chat.cpp` maps an empty language to "Perform ASR.", `audio.input.transcription.language` pins one), the same PCM, `input_audio_buffer.commit` → `conversation.item.input_audio_transcription.completed`. It runs in parallel with the reply (the server has several slots), so it is usually done before the reply ends.
- **llama-server realtime: rates and truncation:** the sample rates come from `session.created` (`audio.input.format.rate`, `audio.output.format.rate`), never hardcoded; `turn_detection` is null (fastrtc's VAD decides). A reply cut off by `max_output_tokens` still reports `response.done` status `completed`; only `usage.output_tokens >= max` shows it (`server-realtime.cpp`: `n_decoded >= n_predict`). Closing the socket mid-reply cancels the server task and frees the slot, and the next session is unaffected; `/v1/models` reports the model's outputs under `data[].architecture.output_modalities`.
- **llamacpp threading:** the `websockets` sync client is not tied to a thread (`sync/connection.py`: sequential `recv()` from different threads works, only concurrent calls raise `ConcurrencyError`; its I/O and keep-alive threads are daemons), but `connect()` blocks for `open_timeout` and `close()` for `close_timeout`, and fastrtc's executor threads are joined at exit. So each session's socket lives on a daemon thread of its own, which never holds the responder directly, and the generator only polls a queue (`POLL_SECONDS`) for `lifecycle.stopping` and `turn.closed`; its `finally` sets the cancel event and the session thread closes the socket (`CLOSE_TIMEOUT` 1 s). `ping_interval=None`: the idle timeout (`VAICE_LLAMACPP_TIMEOUT`) already covers a silent server.
- **Input audio:** llama-server's realtime endpoint wants PCM16 mono at exactly the session's input rate (16 kHz for LFM3-Audio), so `audio.to_pcm16` resamples the browser's 48 kHz audio with `scipy.signal.resample_poly`.
- **A reply error must not escape the generator:** fastrtc wraps the per-connection `emit()` in `webrtc_error_handler` (`webrtc_connection_mixin.py`), so an error that escapes the reply generator comes back as a `WebRTCError`, which the player loop re-raises (`utils.py: player_worker_decode`) — the connection's audio task dies and the page stays mute until a reload. `app.py` therefore catches the error inside the generator, records it on the turn and shows it in the chatbot (`tests/test_interruptible.py` pins both halves); even reading the state back for the UI is guarded, so the generator itself never raises. `conversation.py:_save()` treats a failed write as a warning: the conversation continues in memory and is lost when the app stops.
- **Gradio's `allow_tags` warning:** gradio 5.50 warns that `gr.Chatbot(allow_tags)` will default to `True` in 6.0 *even when you pass `False` explicitly*, so the warning cannot be silenced. Keep `allow_tags=False` in `app.py` anyway, so the upgrade does not start rendering the model's text as HTML.

## Repo conventions

- `tasks/` is local-only and gitignored: `tasks/todo.md` holds the plan/review notes for the current change; `tasks/lessons.md` records lessons after user corrections. Read `lessons.md` at session start if it exists.
- The llamacpp backend is tested against llama.cpp `llama-server` (b11960+) only; keep `responders/llamacpp.py` and the docs honest about that (see README "Requirements").
- Behavior/config changes must update `README.md` (env-var table, layout) in the same change. Adding, removing or re-defaulting a `VAICE_*` variable also updates `.env.example`.
