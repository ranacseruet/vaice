# AGENTS.md

This file provides guidance to coding agents (Claude Code, Codex, Cursor, …) when working with code in this repository. Claude Code reads it through the `@AGENTS.md` import in `CLAUDE.md`.

## What this is

`vaice` is a single-user voice demo: browser mic → fastrtc (WebRTC + VAD) → a `Responder` → spoken reply streamed back, with a persisted multi-turn conversation. Both backends hear the mic audio directly and answer in a speech-to-speech model's own voice: `llamacpp` streams it from a llama.cpp `llama-server` (LFM3-Audio, `/v1/realtime` WebSocket), `native` runs LFM2.5-Audio on MLX. Apple Silicon only (MLX), Python 3.10–3.12 (what CI tests; nothing in the dependencies requires `<3.13` any more). See `README.md` for the user-facing description and the env-var table.

Ruff is configured (`pyproject.toml`: line length 120, lint rules in `[tool.ruff.lint]`); it is not a formatter, so no formatting step. Unit tests use fakes for the models; native tests skip where MLX isn't installed. There is **no automated test against the real models or the browser mic**: verify the audio path by hand (run each `--backend`, ask the same question, check the `[native] time to first audio` log lines).

## Architecture

`app.py` wraps a `Responder` (`responders/base.py`: `respond(audio, history, turn) -> Iterator[(sample_rate, float32 samples)]`) in a fastrtc `ReplyOnPause` handler, logs time to first audio, and shows the conversation in a Gradio chatbot with a "New conversation" button. The page heading and subtitle come from fastrtc's `ui_args` (the subtitle names the backend); the chatbot is 500 px tall and sets `allow_tags=False`, because Gradio 6.0 flips that default to `True` and would render the model's text as HTML. Clicking "New conversation" clears the stored conversation and silences the reply in flight; what you say after the click is the new conversation's first turn, with no earlier turns in the prompt. A 1 s `gr.Timer` re-pushes the chatbot view when it changed (views are deduplicated as JSON), so a native transcript that lands after the reply's final update still replaces the "…". `conversation.py` owns history: `Conversation.start_turn()` closes the previous turn (unfinished = interrupted), `history()` gives the windowed text turns (a turn whose transcript has not arrived yet is dropped from the prompt, so the model never sees a reply to an unreadable question), and everything is saved to `~/.vaice/conversation.json`. Responders report back on the `Turn`: the user transcript (exactly once, even on failure) and the text whose audio was handed out; `app.py` reports the audio seconds handed out, which `Turn.close()` uses to estimate what played (it keeps at least one word, so an interrupted reply is never recorded as empty). `responders/__init__.py:create_responder()` picks the backend: `auto` tries llamacpp (server up and its model outputs audio: `check_server(strict=True)`) and falls back to native with a warning (traceback included); `llamacpp` and `native` fail hard (a llama-server that is merely down is only a warning for explicit `llamacpp`); `cascade` is the old name of `llamacpp` (`BACKEND_ALIASES`). A new backend = implement `Responder` (honour the `Turn` contract in `base.py`) and register it there.

- **`NativeResponder`** (`responders/native.py`): one speech-to-speech model (LFM2.5-Audio via mlx-audio). History goes in as text turns; LFM's ASR mode transcribes the question on the worker after the reply, so the previous turn's transcript can still be pending when the next question arrives — that turn is left out of the prompt until the transcript lands.
- **`LlamaCppResponder`** (`responders/llamacpp.py`): per reply, a fresh `/v1/realtime` session on a daemon thread of its own (`_converse`): `session.update` (instructions = mode line + prompt + the earlier turns as `User:`/`Assistant:` text, `output_modalities` text+audio, `max_output_tokens` 512), the whole utterance as one `input_audio_buffer.append` (mic audio resampled to the session's input rate), `response.create`; `response.output_audio.delta` frames come back through a queue, the text deltas feed `Turn.set_assistant_text` (split by the share of audio, `base.spoken_part`). A second `transcription` session on its own daemon thread (`_transcribe_into`) reports the user's transcript exactly once. Closing the socket cancels the reply on the server.
- **Stopping:** `lifecycle.py` holds the app's stop signal. `app.py:main()` installs the SIGINT handler before anything else, so Ctrl+C sets the flag and gradio closes the server; both backends give up on the reply in flight (the native worker and the llamacpp session threads are daemon threads, so a stuck model call, a server that never answers or one that never completes the websocket upgrade cannot keep the process alive; the generator only polls a queue, so it notices the stop signal within `POLL_SECONDS` even while `connect()` hangs).

Config is entirely env-driven in `config.py` (`VAICE_*`); `--backend` overrides `VAICE_BACKEND`.

## Gotchas (each has bitten this repo)

- **MLX threading:** MLX streams are bound to the creating thread, but fastrtc resumes the reply generator on a different worker thread per chunk. `NativeResponder` therefore loads and runs the model on one dedicated worker thread and hands chunks back through a queue. Any model that creates its own MLX streams must go through a single worker like `NativeResponder`. When testing code that runs inside a framework executor, reproduce its real threading (fresh thread per resume) and confirm the test fails against known-bad code first (a harness that called `emit()` from one thread passed while the live app failed).
- **The MLX worker is a daemon thread, not a `ThreadPoolExecutor`:** `concurrent.futures.thread._python_exit` (registered via `threading._register_atexit`) joins the pool's worker threads at exit, and those are not daemons — a model call that never returns kept the app alive after Ctrl+C (`responders/native.py:_Worker` is a daemon thread of our own instead). The reply generator is resumed on the event loop's default executor (`fastrtc/tracks.py`: `loop.run_in_executor(None, self.event_handler_emit)`), which is not a daemon thread either, so the reply has to be *abandoned* when the app stops, not waited for.
- **The stop signal:** gradio installs no SIGINT handler of its own (`gradio/http_server.py:47 install_signal_handlers` is `pass`; its uvicorn server runs in a daemon thread and `uvicorn/server.py:332 capture_signals` only listens on the main thread), so `lifecycle.py:install_stop_handler()` stays in charge: Ctrl+C sets `lifecycle.stopping` and raises `KeyboardInterrupt`, which gradio's `block_thread` (`gradio/blocks.py:3044`) turns into `server.close()`. `NativeResponder.respond()` polls the flag while it waits for the model and returns without a reply.
- **The queued work must not hold the responder strongly:** the worker holds the task queue, the queue holds the closure, the closure held `self` — and the responder holds the worker: a cycle that kept the worker (and its thread) alive after the responder was gone. The closure uses a `weakref.ref(self)`; the generator keeps the responder alive while the reply runs. The task is dropped before the worker waits for the next one, because the future may hold the exception of a failed reply, whose traceback holds the responder again.
- **fastrtc's idle polling:** `player_worker_decode` (`utils.py`) loops `await loop.run_in_executor(None, handler.emit)` as fast as the executor can schedule it, so an idle connection burned ~64% of a core (~32k `emit()` calls/s, measured). `InterruptSafeReplyOnPause.emit()` waits for the pause event (`self.event.wait(timeout=IDLE_WAIT_SECONDS)`) instead of returning None at once: ~37 calls/s, ~1% of a core. The wait ends as soon as the event is set, so no latency is added — and `emit()` runs in a worker thread (the asyncio default executor in the WebRTC path, an anyio worker thread in the websocket path), never on the event loop.
- **Native chunk decoding:** the detokenizer is stateless, so each 10-frame chunk is decoded with the previous 10 frames as left context, then trimmed. Independent chunk decoding audibly diverged.
- **Single connection:** fastrtc's `Stream` defaults to `concurrency_limit=1`, so a second WebRTC connection is refused (`concurrency_limit_reached`), not queued. A page reload is not affected (Chrome closes the old peer connection on navigation, so the slot is free within ms; measured), but a connection the browser never closes (tab force-closed, browser closed, measured headless via Playwright) holds the slot ~30 s until aioice's consent checks expire (6 failures x ~5 s). The reload console errors `BodyStreamBuffer was aborted` / `Connection errored out` come from Gradio's JS client when the navigation cuts its open `queue/data` event stream (the only request in flight at reload); harmless, and never seen without the chatbot/`additional_outputs`. Barge-in: fastrtc's `close()` on the reply generator fails ("generator already executing") because `emit()` is mid-`next()` on another thread; the reply actually stops when CPython finalizes the dropped generator. The `next()` that was in flight still returns a chunk, which fastrtc would queue after clearing and play (≈ 0.8 s native); `interruptible.py:InterruptSafeReplyOnPause` (what `app.py` uses) drops it by noticing that `receive()` replaced `self.generator` while `emit()` ran. It relies on fastrtc 0.0.34 internals (`generator` is set to None on interrupt; `copy()` must be overridden because fastrtc copies the handler per connection — `interruptible.py:copy()` passes every argument by keyword and `_copy_kwargs()` is checked against `ReplyOnPause.__init__`'s signature in `tests/test_interruptible.py`, so a fastrtc release that adds, drops or reorders a parameter fails there instead of silently misplacing a value), and `tests/test_interruptible.py` drives the real `ReplyOnPause` so a fastrtc upgrade that changes this fails there. A chunk handed to fastrtc just before the interrupt still plays. Replies are capped at 512 tokens on both backends (text + audio frames); truncation is logged. On barge-in (fastrtc acts when the interrupting utterance *ends*), the next `start_turn()` freezes the old turn, so a late finalization can't change history, and cuts its text to the share of audio that could have played since the first chunk (handed out ≠ played: fastrtc's playback queue is unbounded). LFM's interleaved text runs ~2x ahead of its audio, so both backends split text by the share of audio generated (`base.spoken_part`).
- **llama-server realtime: history is text in `instructions`, one fresh session per reply:** `conversation.item.create` with the assistant role is rejected ("only user messages and function call outputs are supported"), so earlier turns can't be replayed as items. A fresh session per reply with the history in `instructions` (set before the first audio/message) is honoured by LFM3-Audio and keeps `conversation.py` the single owner of history (windowing, barge-in cuts, "New conversation").
- **llama-server realtime: no user transcript in a conversation session:** the transcript comes from a second session (`session.update` type `transcription`, no language so the model detects it: `common/chat.cpp` maps an empty language to "Perform ASR.", `audio.input.transcription.language` pins one), the same PCM, `input_audio_buffer.commit` → `conversation.item.input_audio_transcription.completed`. It runs in parallel with the reply (the server has several slots), so it is usually done before the reply ends.
- **llama-server realtime: rates and truncation:** the sample rates come from `session.created` (`audio.input.format.rate`, `audio.output.format.rate`), never hardcoded; `turn_detection` is null (fastrtc's VAD decides). A reply cut off by `max_output_tokens` still reports `response.done` status `completed`; only `usage.output_tokens >= max` shows it (`server-realtime.cpp`: `n_decoded >= n_predict`). Closing the socket mid-reply cancels the server task and frees the slot, and the next session is unaffected; `/v1/models` reports the model's outputs under `data[].architecture.output_modalities`.
- **llamacpp threading:** the `websockets` sync client is not tied to a thread (`sync/connection.py`: sequential `recv()` from different threads works, only concurrent calls raise `ConcurrencyError`; its I/O and keep-alive threads are daemons), but `connect()` blocks for `open_timeout` and `close()` for `close_timeout`, and fastrtc's executor threads are joined at exit. So each session's socket lives on a daemon thread of our own, which never holds the responder (plain arguments only, like the native worker), and the generator only polls a queue (`POLL_SECONDS`) for `lifecycle.stopping` and `turn.closed`; its `finally` sets the cancel event and the session thread closes the socket (`CLOSE_TIMEOUT` 1 s). `ping_interval=None`: the idle timeout (`VAICE_LLAMACPP_TIMEOUT`) already covers a silent server.
- **mlx-audio LFM multi-turn:** `generate_from_chat_state` can't replay earlier assistant audio and prefills from scratch each call, so history is text and only the current clip is audio (one clip per `ChatState`).
- **Input audio:** the native backend takes raw 48 kHz browser audio as-is (mlx-audio resamples internally); llama-server's realtime endpoint wants PCM16 mono at exactly the session's input rate (16 kHz for LFM3-Audio), so `audio.to_pcm16` resamples with `scipy.signal.resample_poly`.
- **A reply error must not escape the generator:** fastrtc wraps the per-connection `emit()` in `webrtc_error_handler` (`webrtc_connection_mixin.py`), so an error that escapes the reply generator comes back as a `WebRTCError`, which the player loop re-raises (`utils.py: player_worker_decode`) — the connection's audio task dies and the page stays mute until a reload. `app.py` therefore catches the error inside the generator, records it on the turn and shows it in the chatbot (`tests/test_interruptible.py` pins both halves); even reading the state back for the UI is guarded, so the generator itself never raises. `conversation.py:_save()` treats a failed write as a warning: the conversation continues in memory and is lost when the app stops.
- **Gradio's `allow_tags` warning:** gradio 5.50 warns that `gr.Chatbot(allow_tags)` will default to `True` in 6.0 *even when you pass `False` explicitly*, so the warning cannot be silenced. Keep `allow_tags=False` in `app.py` anyway, so the upgrade does not start rendering the model's text as HTML.

## Repo conventions

- `tasks/` is local-only and gitignored: `tasks/todo.md` holds the plan/review notes for the current change; `tasks/lessons.md` records lessons after user corrections. Read `lessons.md` at session start if it exists.
- The llamacpp backend is tested against llama.cpp `llama-server` (b11960+) only; keep `responders/llamacpp.py` and the docs honest about that (see README "Requirements").
- Behavior/config changes must update `README.md` (env-var table, layout) in the same change. Adding, removing or re-defaulting a `VAICE_*` variable also updates `.env.example`.
