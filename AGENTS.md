# AGENTS.md

Guidance for coding agents (Claude Code, Codex, Cursor, …) working in this repository. Claude Code reads it through the `@AGENTS.md` import in `CLAUDE.md`.

## What this is

`vaice` is a single-user voice assistant for the Mac: browser mic → fastrtc (WebRTC + VAD) → **one speech-to-speech session per reply** with llama.cpp `llama-server` (`/v1/realtime`, LFM3-Omni-2B Q8_0 by default) whose tools are vaice's own skills (disk, battery, apps, volume, files; opt-in shell, memory, screen, MCP tools, browser tasks) → the model's speech streams back. Python 3.12 only; CI runs on macOS, other OSes are not validated. User docs: `README.md` and `docs/` (`docs/README.md` is the index, `docs/configuration.md` the env-var table, `docs/architecture.md` the design and code map, `docs/vision.md` the roadmap).

The architecture is deliberately small (decided 2026-11-19, after a spike measured the trade-off): one model, one session per reply, everything vaice must be sure of is a button. Do not reintroduce a second model, a separate STT/TTS step, spoken approval or multi-step task budgets without the user asking for it.

## Commands

```bash
uv sync --extra dev                                   # setup (.venv from uv.lock; add --extra mcp and --extra browse for their tests)
.venv/bin/pytest                                      # all tests (with coverage, see pyproject addopts)
.venv/bin/pytest tests/test_realtime.py -k history    # one test
.venv/bin/ruff check .                                # lint (no formatter)
.venv/bin/vaice                                       # run; UI at http://127.0.0.1:7860 (llama-server started separately)
.venv/bin/vaice up                                    # same, but starts llama-server first when none is running
.venv/bin/python evals/run.py --repeats 1 --cases open-safari,know-sky   # live skill-calling eval (needs llama-server)
```

Unit tests use fakes (`tests/fake_realtime.py` is a fake `/v1/realtime` server). Nothing automated runs against a real model or a real mic: verify the audio path by hand (run vaice against a compatible llama-server, ask something, check the `time to first audio` log line; drive a test browser muted, `--mute-audio`). Claims about model behaviour (call rate, a prompt's effect) come from `evals/` with repeats, per build/model/quantization, never from single runs; CI does not run the eval.

## Architecture

```
mic ─ fastrtc ReplyOnPause (interruptible.py) ─ app.make_handler ─ Assistant.respond (assistant.py)
                                                                      └ RealtimeResponder (realtime.py): one /v1/realtime session
                                                                          tools = Skills.definitions(), calls -> assistant._Executor
                                                                          + a parallel transcription session -> Turn.set_user_text
speech with no reply in flight (after Run, a browser task's outcome) ─ realtime.speak (text in, speech out, no tools)
                                                                      ─ Outbox ─ served by the idle emit() (interruptible.py)
```

- `app.py`: CLI, startup checks, the Gradio UI (chatbot, *New conversation*, the confirmation panel with Run/Cancel, *Stop the browser task*, *Tool activity*, *Memory*), a 1 s timer that re-pushes views when they changed (JSON-deduplicated). The chatbot sets `allow_tags=False` (Gradio 6 flips the default and would render model text as HTML).
- `realtime.py`: the session machinery (below), `speak`, `check_server` (rejects a model without audio output; a server that is down or loading only warns).
- `assistant.py`: `Assistant`: builds the instructions (prompt + memory notes) and a per-reply `_Executor`; Run/Cancel (`approve`/`cancel`), *New conversation* (`clear_pending`), the browser task (`_browse` thread, `stop_task`, `browsing`).
- `skills.py` (built-in skills, `Skill` kinds), `confirm.py` (the one pending request), `shell.py`, `memory.py`, `vision.py`, `mcp_skills.py`, `acp_agent.py` (`AcpAgent`, the ACP client of the browser task; needs the `browse` extra, imported lazily) + `browse.py` (the `BrowseAgent` protocol, the Pi and generic-ACP presets, the profile sweep) + `browse_task.py` (the browse skills, status) + `browse_gate.ts` (Pi extension), `conversation.py` (turns, history, `conversation.json`), `outbox.py`, `interruptible.py`, `server.py` (`vaice up`), `config.py`, `lifecycle.py`, `audio.py`.

Rules that hold the design together:

- **History is text only.** `Conversation.history()` gives the windowed turns as ChatML in the session's instructions; a turn whose transcript has not arrived is dropped. Skill results are tool events on the `Turn` (*Tool activity*, `conversation.json`), never replayed to the model: a follow-up calls the skill again. The responder reports the transcript exactly once (also on failure) and only text whose audio was handed out; `Turn.close()` trims an interrupted reply to the share that could have played (at least one word).
- **Skill kinds** (`Skill.kind`): `read` and `action` run at once on the session thread; `confirm` (`quit_app`, `run_shell`, `forget_everything`, MCP `click` tools) becomes ONE `Pending` in `Confirmations` at once and the model is told only the Run button runs it (`WAITING`); `background` (`browse`) starts a task and returns at once. The executor and every skill never raise: a failure is the result the model reads. `remember` (`direct_only`) is refused once any other skill was called in the same reply (a file name, a page, a command's output must not become a note).
- **Confirmation is button only.** Run (`approve(id)`) takes the request atomically and id-bound, runs the STORED name and arguments, records the result on the asking turn and speaks the outcome through `speak` with `APPROVED`; Cancel records `cancelled` and says nothing. A spoken yes can come from speaker echo, so nothing is approved by voice. Expiry `CONFIRM_SECONDS` (60) from asking; a newer request replaces an older one. *New conversation* bumps `Confirmations.epoch`: each reply's `_Executor` takes it when the reply begins, and `ask`, `_start_browse` and the task's step questions refuse a stale one, so a reply still preparing a call (`quit_app` asks `lsappinfo`) leaves nothing approvable in the new conversation.
- **The browser task** (`VAICE_BROWSE=pi|acp`) runs on a daemon thread, one at a time; an utterance does not stop it, the Stop button, `stop_browsing`, *New conversation*, app exit and `VAICE_BROWSE_SECONDS` do. A gated step is a waiter-kind `Pending` (button only, with a spoken heads-up); its outcome is recorded on the asking turn and spoken through `speak` (`REPORT`; fixed failure sentences through `SAY`). `browser_status` reads `BrowseStatus`. The agent is an ACP client (`AcpAgent`): one long-lived agent process, a fresh `session/new` per task, every permission request goes to `on_ask` (the Run button). The agent's Chrome is not in its process group: `browse.end_profile_processes` ends whatever holds the profile, before a new agent process starts and after `close()`.
- **Untrusted text** (tool output, MCP descriptions, page text, screen text, notes) only ever reaches the model as a tool result or as cleaned, capped prompt text; secrets (`*_API_KEY`, MCP `env`) never reach a log, an error or a repr, and tests grep for fake keys. `config.REMOVED` names settings that no longer exist; `app.main()` warns once with names only.
- **Config** is env-driven (`config.py`, `VAICE_*`), loading a `.env` from the working directory (environment wins). `tests/conftest.py` chdirs to an empty temp dir at import so a developer's `.env` cannot change test expectations, and isolates `VAICE_DATA_DIR`.

## Measured choices: do not undo without a live A/B

Each line was measured on the live eval or a live probe; the numbers and runs are in `docs/` and the PRs.

- Default model LFM3-Omni-2B **Q8_0** (4-bit backbones drifted). Server with `--temp 0`: the realtime API has no temperature field, and at the default 0.8 a 2B model drifts (`check_server` warns).
- Memory, shell and vision are **off by default**: each extra tool cost accuracy on ordinary requests. Accuracy falls as the tool count grows (spike 2026-11-19, 53 cases x 5: 83% of runs right on this path).
- `volume_up`/`volume_down` are argument-free skills (as a `direction` argument the model guessed a level); no `web_search` skill (the model searched for things it knew).
- `memory.clean_note` refuses notes under 3 words ("Goodbye"), notes bound to a moment (reminders: nothing in vaice fires later) and the user's own question; the `remember` description says it is not for reminders.
- Vision: 1024 px screenshots, `VAICE_VISION_MAX_TOKENS` 200 plus a "one or two short sentences" system line (without both: 4 to 9 s answers and timeouts); the prompt line "The computer changes all the time … use the tool again" and `look_at_screen`'s "never answer from an earlier look".
- The clock line is imperative ("You know the current date and time: … Use it when asked …"); a declarative line was ignored. Prompt lines that forbid things ("do not read the result aloud") broke the audio (silent replies): don't add one without an A/B (#77).
- `APPROVED` (the Run outcome's wording): `REPORT` turned "quit Calculator" into "Sure, here's your request: quit Calculator." (probe, one run per wording).
- `browse.PROMPT` says Bing or DuckDuckGo, never Google (bot checks); don't configure a browser MCP server next to `browse` (the model mixed the two).

## Gotchas (each has bitten this repo)

- **fastrtc threading:** fastrtc resumes the reply generator on a different worker thread for each chunk. Code that runs inside it must not be bound to a thread, and tests must reproduce it (fresh thread per resume: the one harness is `tests/threads.py`); confirm such a test fails against known-bad code first.
- **Realtime sessions live on daemon threads:** each session's socket is on a daemon thread of its own and the generator only polls a queue (`POLL_SECONDS`) for `lifecycle.stopping` and `turn.closed`; its `finally` sets the cancel event. `connect()` blocks for the open timeout and `close()` for the close timeout, and fastrtc's executor threads are joined at exit, so nothing blocking may run on them. llama-server (b12359) never completes the close handshake: the close runs on one more daemon thread (waiting for it delayed every transcript by 1 s, #90). `ping_interval=None`.
- **The stop signal:** gradio installs no SIGINT handler (its uvicorn runs in a daemon thread), so `lifecycle.install_stop_handler()` does: Ctrl+C sets `lifecycle.stopping` and raises `KeyboardInterrupt`, which gradio's `block_thread` turns into `server.close()`.
- **fastrtc's idle polling:** the player loop calls `emit()` as fast as it can (~32k calls/s, 64% of a core idle). `InterruptSafeReplyOnPause.emit()` waits on the pause event (`IDLE_WAIT_SECONDS`) instead: ~37 calls/s, no added latency.
- **Barge-in races** (`interruptible.py`, fastrtc 0.0.34 internals, pinned by `tests/test_interruptible.py` driving the real `ReplyOnPause`): `close()` on the running generator fails ("generator already executing"); the chunk from the `next()` in flight is dropped by noticing `receive()` replaced `self.generator`. If the reply ends while a barge-in pause is pending, fastrtc's `reset()` would wipe the new utterance (#13): `emit()` snapshots and restores it (only for its own end-of-reply reset, never when newer audio exists, never when the reply began from that pause). `copy()` passes every argument by keyword and `_copy_kwargs()` is checked against `ReplyOnPause.__init__`, so a fastrtc upgrade fails a test instead of misplacing a value. A connection the browser never closes holds the single slot (`concurrency_limit=1`) ~30 s.
- **One utterance at a time:** a Run outcome, a step's heads-up and a task's outcome come from different threads; `Assistant._say` holds `_speech_lock` around `speak` (two sessions writing to one outbox interleaved their frames) and takes the outbox generation before it waits, so a clear while waiting still cancels it.
- **The outbox must be paced:** fastrtc plays what an idle `emit()` returns, and its playback queue is unbounded, so the idle `emit()` serves the next frame or marker only while the audio served so far (reply audio included) ends less than `LEAD_SECONDS` (0.4) ahead; otherwise markers (the recorded text) fire long before playback and a clear finds nothing. Speech start clears the outbox (and fastrtc's queue while proactive audio is still playing); every `clear()` starts a new `generation` that `put` refuses, so a cancelled `speak` queues nothing more; an outbox nobody polled for `STALE_SECONDS` (30) is cleared before serving.
- **VAD:** fastrtc's default Silero options (2000 ms silence inside 600 ms chunks) inflate noise into speech and clip the first words; `DEFAULT_VAD_OPTIONS` (`VAICE_VAD_*`) plus a 0.3 s pre-roll fix both.
- **History is ChatML in `instructions`:** `conversation.item.create` rejects the assistant role, so each reply is a fresh session whose instructions close the system block and add each past turn as `<|im_start|>{role}` (control tokens stripped from turn text); a flat transcript made 2B models mix roles and loop.
- **Transcription is a second session** (type `transcription`, no language: pinning `en` measurably repeats the passage), run in parallel with the reply.
- **Rates and truncation:** sample rates come from `session.created`, never hardcoded; mic audio is resampled to the input rate (`audio.to_pcm16`). A reply cut off by `max_output_tokens` still says `completed`; only `usage.output_tokens >= max` shows it. 1024 tokens (512 truncated most replies: 12 audio tokens per 80 ms).
- **Do not pin language/voice** (`--tts-lang`, `--tts-voice`, `audio.output.*`): unnecessary for English, and an injected speech line degraded a reply once; the parroting it was blamed for did not reproduce.
- **Tools are declared flat** (Responses format, `{"type": "function", "name", …}`): the chat-completions nesting is rejected. `tool_choice: "required"` is not enforced with audio output; follow-ups are created with `auto` (an inherited `required` made the model call again and loop) and the round at `MAX_TOOL_ROUNDS` (2) with `none` (a call there is ignored). The model reads tool results aloud, so results are compacted (`_speech_friendly`, `VAICE_LLAMACPP_TOOL_*_CHARS`). Text before a tool result is spoken but not recorded (each round has its own accumulator; frames carry a reference to theirs). `_MarkupStripper` removes `<tool_call>`, `</think`, `<|…|>` and `<answer>` markup across deltas. A 1–4-line block repeated 3× is cut and the socket closed (greedy decoding loops to the cap otherwise).
- **A reply error must not escape the generator:** fastrtc turns it into a `WebRTCError` that kills the connection's audio until a reload. `app.make_handler` records it on the turn and shows it in the chatbot; even that is guarded. A failed `conversation.json` write is a warning.
- **ACP browser agent** (`acp_agent.py`, pinned `pi-acp@0.0.34`, SDK `agent-client-protocol` 1.0): `pi-acp` ignores `mcpServers` in `session/new` (Pi's own `mcp.json` holds the browser server), closes the other sessions' `pi` (and so Chrome) on every `session/new`, and does not advertise `session/close` (sent only when advertised). A **no must also cancel**: the reject option alone makes the model route around it, so a no is answered, then `session/cancel`, then `BrowseDeclined`, and a response always goes out before the cancel that follows it. The **answer is the text after the last tool call** (earlier text is chatter, and for Pi, start-up text). The SDK runs notifications and requests as separate tasks in arrival order: a handler must not await before it mutates state, and updates count only after the prompt is sent (pi-acp reuses the session id across tasks). The SDK logs a handler's exception text on the root logger, so handlers catch everything and log type names only. The `browse` extra is imported lazily (`import acp` only in `acp_agent.py` and where an agent is built).
- **The Pi gate is checked twice.** A gate that loads without hooking in leaves Pi's browser tools ungated (measured with Pi 1.5.2: one that throws while loading stops Pi from starting; an empty one runs and only the two checks catch it). `browse.check_gate` (startup: a real Pi must list `vaice-gate`) and the tripwire (every task: `notify("vaice-gate <nonce>")` before the first tool call or permission request, else the request is answered cancelled and the agent ended). `AcpAgent` reads the timing constants as `browse.X` at call time, so tests shorten them with `monkeypatch.setattr(browse, ...)`.
- **macOS specifics:** `quit_app` checks `lsappinfo list` first (AppleScript's `is running` hangs on a chooser and `quit` launches a missing app); `screencapture` failing with `could not create image` means the launching app (the terminal) lacks Screen Recording permission.
- Gradio 5.50 warns about `allow_tags` even when it is passed: keep `allow_tags=False` anyway.

## Repo conventions

- `tasks/` is local-only and gitignored: `tasks/todo.md` (plan, decisions), `tasks/lessons.md` (read at session start).
- Tested against llama.cpp `llama-server` b11960+ only; keep `realtime.py` and the docs honest about that (`docs/installation.md`).
- Behaviour/config changes update the matching `docs/` page in the same change (an env var: `docs/configuration.md` and `.env.example`; how the pieces fit or the code layout: `docs/architecture.md`; a roadmap item: `docs/vision.md`), `README.md` when the quickstart or the feature list changes, and `CHANGELOG.md`.
