# AGENTS.md

This file provides guidance to coding agents (Claude Code, Codex, Cursor, …) when working with code in this repository. Claude Code reads it through the `@AGENTS.md` import in `CLAUDE.md`.

## What this is

`vaice` is a single-user voice demo: browser mic → fastrtc (WebRTC + VAD) → a `Responder` → spoken reply streamed back, with a persisted multi-turn conversation. The `llamacpp` responder sends audio to llama.cpp `llama-server` (LFM3-Omni-2B Q8_0 by default, `/v1/realtime` WebSocket; LFM3-Audio-2B also works) and streams the model's speech back. Python 3.12 is the one supported and CI-tested version; CI runs on macOS, and other OS audio behavior is not validated. See `README.md` for the user-facing description and `docs/` for the rest (`docs/configuration.md` is the env-var table, `docs/architecture.md` the design and the code map, `docs/vision.md` the north star; `docs/README.md` is the index).

## Commands

```bash
uv sync --extra dev                              # setup: .venv from the committed uv.lock (py 3.12 from .python-version)
.venv/bin/pytest                               # all tests
.venv/bin/pytest --cov=vaice --cov-report=term-missing  # tests with line coverage
.venv/bin/pytest tests/test_llamacpp.py -k history      # single test
.venv/bin/vaice                                   # run; UI at http://127.0.0.1:7860 (llama-server started separately)
.venv/bin/vaice up                                # same, but starts llama-server first when none is running
.venv/bin/python evals/run.py --repeats 1 --cases open-safari,know-sky   # live tool-calling eval (needs llama-server; see evals/README.md)
.venv/bin/python evals/run.py --paths assistant --repeats 1              # the same for assistant mode (its own cases and skills)
```

Ruff is configured (`pyproject.toml`: line length 120, lint rules in `[tool.ruff.lint]`); it is not a formatter, so no formatting step. Unit tests use fakes for the server and model responses. There is **no automated test against a real model or the browser mic**: verify the audio path by hand (run vaice with a compatible llama-server, ask a question, and check the `[llamacpp] time to first audio` log line). Claims about how the model behaves (tool-call rate, a prompt's effect) come from the live eval in `evals/` with repeats, per build/model/quantization, not from single runs; only its scoring logic is unit-tested and CI does not run it.

## Architecture

`app.py` wraps a `Responder` (`responders/base.py`: `respond(audio, history, turn) -> Iterator[(sample_rate, float32 samples)]`) in a fastrtc `ReplyOnPause` handler, logs time to first audio, and shows the conversation in a Gradio chatbot with a "New conversation" button. At startup `main()` checks llama-server, then constructs `LlamaCppResponder` directly; a server that is unreachable or loading warns and the UI still starts, while a reachable model without audio output is rejected. The page heading and subtitle come from fastrtc's `ui_args`; the chatbot is 500 px tall and sets `allow_tags=False`, because Gradio 6.0 flips that default to `True` and would render the model's text as HTML. Clicking "New conversation" clears the stored conversation and silences the reply in flight; what you say after the click is the new conversation's first turn, with no earlier turns in the prompt. A 1 s `gr.Timer` re-pushes the chatbot view when it changed (views are deduplicated as JSON), so a transcript that lands after the reply's final update still replaces the "…". `conversation.py` owns history: `Conversation.start_turn()` closes the previous turn (unfinished = interrupted), `history()` gives the windowed text turns (a turn whose transcript has not arrived yet is dropped from the prompt, so the model never sees a reply to an unreadable question), and everything is saved to `~/.vaice/conversation.json`. The responder reports the user transcript (exactly once, even on failure) and text whose audio was handed out on `Turn`; `app.py` reports the audio seconds handed out, which `Turn.close()` uses to estimate what played (it keeps at least one word, so an interrupted reply is never recorded as empty).

- **Default model: LFM3-Omni-2B `Q8_0`** (`VAICE_LLAMACPP_MODEL`; was LFM3-Audio-2B `Q4_K_M` until 2026-11-17). Omni speaks, listens and reads images, so one server serves chat mode, assistant mode (transcription, brain, `/tts`) and `look_at_screen`; Q8_0 is about 2.4 GB to download and 4 GB in memory, and earlier side-by-side runs (`docs/troubleshooting.md`: Q8_0 matches the unquantized model, 4-bit backbones drift) are why 8-bit rather than 4-bit. **Measured on llama-server b12359, `--temp 0`, one run per setting, 5 repeats of 51 assistant cases:** 250/255 with memory, vision and shell off (Audio-2B Q4_K_M: 225/255), median time to answer text 0.93 s; with vision offered 235/255 (`files-screenshot`, `volume-down` 5/5 to 0/5); with memory and vision both offered 235/255 on the same 51 plus 60/80 on the 16 memory cases (`memory-forget-*`, `memory-no-reminder-dentist` and `memory-no-question-as-note` 0/5, `no-skill-reminder` 0/5); the 11 vision cases 50/55 (`vision-dialog` 0/5, as on Audio-2B). Interleaved (chat with the server's tools) 69/99, three repeats: not compared with Audio-2B, so no claim either way. **Browser check** (headless Chrome, spoken clip, a temp `VAICE_DATA_DIR`): assistant mode answered the disk question from `disk_space` in 1.2 to 1.6 s to first audio (transcript 0.2 s), chat mode answered a general question at 0.4 s to first audio (without `--tools` it says it cannot see the disk, as expected). **So the other defaults stay as they are:** memory, shell and vision are off because each costs points on ordinary requests (see their bullets), and `VAICE_MODE` stays `chat` (assistant mode runs actions on the machine, which should be a choice). Not verified: Omni with `--tools` in the browser, Linux/Windows, a build other than b12359.
- **`LlamaCppResponder`** (`responders/llamacpp.py`): per reply, a fresh `/v1/realtime` session on a daemon thread of its own (`_converse`): `session.update` (instructions = mode line + prompt + the earlier turns as ChatML `<|im_start|>user` / `<|im_start|>assistant` blocks + the local-time context line, `output_modalities` text+audio, `max_output_tokens` from `VAICE_LLAMACPP_MAX_OUTPUT_TOKENS`), the whole utterance as one `input_audio_buffer.append` (mic audio resampled to the session's input rate), `response.create`; `response.output_audio.delta` frames come back through a queue, the text deltas feed `Turn.set_assistant_text` (split by the share of audio in the current round, `base.spoken_part`; around a tool round only the final round's text is recorded — the preamble is spoken but dropped). A second `transcription` session on its own daemon thread (`_transcribe_into`) reports the user's transcript exactly once. Closing the socket cancels the reply on the server; closing it early on a detected repetition loop frees the slot too.
- **`vaice up`** (`server.py`, `ensure_server()`): `main()` calls it after `install_stop_handler()` and before `check_server()`, and passes `inbrowser=True` to `launch()`; plain `vaice` skips all of it. A `/health` that answers 200 or 503 means reuse (nothing started, nothing stopped later). Otherwise the URL's host must be `localhost`/`127.0.0.1`/`::1`, `llama-server` must be on `PATH` (never installed for the user) and its `--version` build (`build N`) must be at least `MIN_BUILD` (11960; an unparseable version only warns). The child is `llama-server -hf VAICE_LLAMACPP_MODEL --temp 0 --host H --port P` + `VAICE_LLAMACPP_SERVER_ARGS` (shlex-split in `config.py`), in its own session so the terminal's Ctrl+C reaches only vaice, with output appended to `<DATA_DIR>/llama-server.log` (a temp dir when `DATA_DIR` is None). The wait polls `/health` every `POLL_SECONDS` and ends with a `SystemExit` when the child exits, `VAICE_LLAMACPP_START_TIMEOUT` passes or `lifecycle.stopping` is set; any exit from the wait (including Ctrl+C) stops the child first. `ManagedServer.stop()` (terminate, wait `STOP_WAIT`, kill; idempotent) runs in `main()`'s `finally`, with `atexit` as a backstop that `stop()` unregisters. Tests use fakes for `requests`, `subprocess` and `shutil.which` only (`tests/test_server.py`); the real start is not tested.
- **`AssistantResponder`** (`responders/assistant.py`, `VAICE_MODE=assistant`, default chat unchanged): separate steps instead of one speech-to-speech session. One daemon thread (`_work`, same model as `LlamaCppResponder`: the generator only polls a queue every `POLL_SECONDS` and checks `lifecycle.stopping` / `turn.closed`; its `finally` sets the cancel event; a worker error is queued and re-raised in the generator) runs: `_transcribe` (the realtime transcription session; `Turn.set_user_text` exactly once, via try/finally, even when it fails) → `decide()` (`brain.ChatBrain` = `POST /v1/chat/completions`, temperature 0, tools in chat-completions nesting; skills run by vaice itself in `skills.py`, reported with `Turn.add_tool_event` on the worker thread; a **task** (`Task` in `assistant.py`, `VAICE_ASSISTANT_MAX_STEPS`, default 10, >= 2, and `VAICE_ASSISTANT_TASK_SECONDS`, default 120, from `AssistantResponder(max_steps=, task_seconds=)`) bounds the brain calls: `decide(..., task=)` calls the brain until it answers with no skill call, and the call `Task.final()` names, the one that leaves no step or finds the deadline passed (checked between calls: one in flight is not cut off), is made without `tools` so it must answer, a skill call in it is ignored and logged; each call counts in `task.steps`; **taint is the task's (`task.tainted`), not one `decide()` call's**, so it survives a confirmation question and the continuation after a yes) → `voice.speakable()` + `voice.sentences()` → one streamed `POST /tts` per sentence (`pcm16`, rate from the `Content-Type` `rate=` parameter, an odd trailing byte carried into the next chunk). Text is recorded sentence by sentence as its audio is queued (`Turn.set_assistant_text`), so a barge-in keeps what was spoken. Skills never raise (`Skills.run` speaks failures), and run argv lists with a timeout and no shell (the first five are read-only; the actions are in the next bullet); llama-server's `--tools` and `VAICE_LLAMACPP_TOOLS` are unused here. First audio is 0.6–1.7 s on b12359 (transcript 0.12–0.18 s, after #90). **History carries skill results only in assistant mode**: a responder with `tool_history = True` (the optional `Responder` attribute, read by `app.py` with `getattr`) gets `Conversation.history(before, tools=True)`, which puts each answered turn's tool events between its user and assistant messages as `("tool", "<name>: <output>")` (output capped at `TOOL_HISTORY_OUTPUT_CHARS`=300, same windowing and pending-transcript rules; a turn with no spoken text carries none), and `build_messages` turns them into a real tool exchange (one assistant message with the turn's `tool_calls`, ids `h<N>`, then a `tool` message each). **A call that asked for confirmation is stored as two events** (`conversation.WAITING_FOR_CONFIRMATION`, then its result, `cancelled`, `not confirmed` or `expired`; also every `auto` call), and `to_messages` leaves the wait out of the replay once a later event of the same turn has the same name and arguments (a call still waiting keeps its one entry): with real arguments replayed, the model was shown the call twice in one assistant message and copied the pair, sending every call twice (`take_snapshot` x2, `navigate_page` x2, seen in a real LM Studio request log). Only the replay changes: the stored events, `conversation.json` and the *Tool activity* panel keep both. **The replayed call carries its real arguments:** with `{}` replayed, the 24B helper brain copied `chrome__take_snapshot {}` from history and left the required `pageId` out (a real saved conversation: 1 of 8 first replies carried it with `{}` replayed, 8 of 8 with the real arguments). A call with arguments is the history entry `("tool", conversation.tool_entry(name, arguments, output))`, a JSON object `{"name", "arguments", "output"}` (a plain `"<name>: <output>"` entry, which has no arguments, never starts with `{`, so `parse_tool_entry` tells them apart without splitting on `": "`); `replay_arguments` keeps the stored string only when it parses to a JSON object and its compact form (`separators=(",", ":")`, `ensure_ascii=False`) is at most `TOOL_HISTORY_ARGUMENT_CHARS`=300, else `{}`: never truncated, since cut-off JSON is invalid and hosted endpoints reject it. Stored events and `conversation.json` are unchanged. Eval case histories can carry arguments (`evals/README.md`). Without that the next turn only saw the spoken text, and a follow-up ("and how much memory?") was answered from the model's head (8 gigabytes on a 48 gigabyte Mac). `LlamaCppResponder` has no `tool_history`, so chat mode's history is unchanged. `top_processes` speaks cleaned names (`speakable_process_name`: no trailing parenthetical, `Helper` counted with its app, reverse-DNS reduced to its last part), aggregated then sorted; the detail keeps the raw rows. The live eval has an `assistant` path (stub skills, nothing executed; not in the default `--paths`).
- **Action skills and confirmation** (`skills.py`, `confirm.py`, assistant mode only): a `Skill` has a `kind`: `read` and `action` run at once, `confirm` asks first. `open_app`, `set_volume` (a required `level`), `volume_up`, `volume_down` (argument-free, `VOLUME_STEP` = 10 from the current volume, clamped) and `mute_sound` are actions and `quit_app` is the one confirm skill; all validate through `Skills._resolve` (shared by `run` and `prepare`), use argv lists and never raise. Action results must name their object (`opened Safari`, `volume set to 40 percent`): history replays a call's arguments only as compact JSON of at most 300 characters (a longer object, an entry from before that change or an event with none replays as `{}`), so a follow-up may have to be answered from the result text alone. `quit_app` checks the app is running with `lsappinfo list` (foreground apps, case-insensitive, canonical name used) before `tell application (item 1 of argv) to quit`: both AppleScript `application X is running` and `quit` on a missing app misbehave (the former hangs on a chooser, the latter launches the app first). `decide()` calls `Skills.prepare` for a confirm skill: it returns a `Question` (or raises `SkillError`, answered as an ordinary failed call), the loop stops at it, calls after it in the same round are dropped (logged), and the assistant message's `tool_calls` are truncated to those up to and including it so the stored chat stays valid. `Confirmations` holds one thread-safe `Pending`: `ask` (visible in the UI at once) then `arm` only after the question's audio was handed out (by the reply generator, when it reaches the `_Asked(spoken=True)` marker the worker queued behind the last frame: the worker itself only knows the frames are queued, and `/tts` runs ahead of playback; the generator's `finally` drops a request whose question it did not hand out to the end) (an unarmed request cannot be answered and never expires; a question cut off or failed is dropped); expiry is `CONFIRM_SECONDS` (60) counted from arming; `take(id)` is atomic and id-bound, so a click and a spoken yes cannot both run it. The question text must contain no yes/no words, because speaker echo can reach the mic. The next reply's transcript is tested with `spoken_answer`: only a whole utterance equal to a yes phrase approves (`yes` runs the stored name and arguments, never what the brain says now, then `decide()` goes on in the same task, `Pending.task`, tainted because the approved call is a tool result, with tools: the brain says how it went, calls more skills or asks another question, which `_work` speaks, arms and waits for like any other; an empty answer speaks the approved call's result, and a `BrainError` in the continuation speaks it too (the call ran) with the skills that ran since kept in `calls`). **A click or an `auto` run continues the task too, and speaks the outcome** (#110, see the next paragraph of this bullet); a no phrase cancels ("Okay, I won't."); anything else drops the request, records `not confirmed` on the asking turn and is handled as a new question. An empty transcript (noise) is none of these: `NOT_HEARD` is spoken and the request stays, by choice (a cough must not cancel it; the next understood utterance settles it). A click goes through `AssistantResponder.approve/cancel(id)`; `approve`'s return value and the result event it records on the asking turn (`Turn.add_tool_event` works on a closed turn) are unchanged, `cancel` continues nothing. **After `approve` ran a call (not one that was stopped), `_start_continuation` starts a daemon thread `vaice-assistant-task` running the module-level `_continue`** (plain data, never `self`): the same `Task` as the question's (`pending.task`, or a fresh one), `task.tainted = True` (the approved result is a tool result, so `decide()` gives any `auto` skill its click fallback and refuses `remember` by itself; `decide()` is unchanged), `decide()` over `pending.messages` + the tool message with events recorded on the asking turn; a `_Stopped` ends it quietly and any other failure (`BrainError` included: the call already ran) logs a warning and speaks the call's own result. It ends in an answer or in another confirmation question: that `Pending` has `auto_seconds` forced to 0 (a countdown inside a continuation is the next stage, B2b; logged), is `ask`ed at once (the panel shows it) with its `waiting for confirmation` event, and is armed by the last outbox marker (`confirmations.arm`) whose `on_drop` is `confirmations.take` (a question nobody heard must not stay answerable or clickable; also taken when its speech fails or has no audio). **One task at a time**: the responder holds the running continuation's cancel `Event`; a new `approve`, `respond()` (a new utterance, which also clears the outbox) and `clear_pending()` (also clears the outbox) set it, and `stop()` for the continuation is that event or `lifecycle.stopping`. An approval still running its call when one of those cancels (`_cancel_task` bumps `_task_epoch`, which `approve` captured when it began, and `clear_pending` also sets the run's own cancel event) starts no continuation: `_start_continuation` checks both under the task lock, atomic with the registration (Codex P1s on #115). **The outcome is spoken through the `Outbox`** (`outbox.py`; `app.build_stream` creates one for a responder that has the optional `attach_outbox`, passes it to the handler and the responder; chat mode has none): `_speak` writes into an `_OutboxSink` that puts `(rate, frame)` on it and, after each sentence's frames, a marker that calls `Turn.append_assistant_text(sentence)` (thread-safe, works on a CLOSED turn: the one deliberate exception to the freeze, `set_assistant_text` still ignores one), so the spoken text is recorded only when its audio was SERVED and a barge-in that clears the outbox leaves the rest unrecorded; the bubble then reads `<question> <outcome>` and `to_messages` carries it. With no outbox attached the continuation still runs, records and asks (armed at once) but nothing is spoken or appended. **Not verified: this is unit-tested with fakes (fake brain, skills and `/tts`, the real `ReplyOnPause` machinery for the handler); the real audio path (fastrtc playback of idle `emit()` audio, speech-start clearing, the browser) is checked separately by hand.** A voice yes is unchanged: it continues inside the reply generator (`_approved`). `app.py` shows a hidden `gr.Column` above *Tool activity* (assistant mode only, found by `getattr(responder, "pending", None)`) with the question and the exact call; its `gr.State` holds the id the panel showed, and a click blanks `seen` so the next timer tick redraws. The live eval stubs `ask` for confirm skills (always asks) and counts the pending call as the call; the confirmation flow itself is covered by unit tests only. **Two live-eval lessons, do not undo them without a live A/B:** (1) a `web_search` skill (open a Google search) made the 2B model search for questions it could answer itself ("why is the sky blue", "capital of France", the weather); the eval went from 170/175 to 185/245 and rewording its description did not help, so it is removed until the helper model (phase 4) can decide when a search is warranted; the `no-skill-search-*` cases keep it that way. (2) Relative volume is two argument-free skills (`volume_up`, `volume_down`), not a `direction` argument of `set_volume`: as an argument the model guessed a level or asked how much. The eval's `ACTION_STUBS` answer from their own arguments (`opened Calculator` for a Calculator request) because a canned "opened Safari" made the model call again. The brain's final answer goes through `_spoken_text` (`llamacpp._MarkupStripper` over the whole string): the model sometimes writes `<tool_call>...` as prose in the round made without tools, which would be spoken; an unterminated block is dropped to the end, an answer that is nothing but bracket-style pseudo calls (`[open_file(path='old_report.docx')]`, `[find_files(name='resume*', path='/home')]`; a helper model's final answer in the full eval, which would be read aloud) is dropped too (`_PSEUDO_CALLS` full match, one or more `[identifier(...)]`; ordinary text with brackets is untouched), an answer left empty becomes `NO_ANSWER` (after an approval, the skill's result text) and a warning is logged.
- **Shell skill** (`shell.py`, `VAICE_ASSISTANT_SHELL`, default off; `default_skills(shell=True)` adds `run_shell`, and `skills.py` imports `shell` lazily because `shell` imports `skills`): a `confirm` skill whose `ask` returns a `Question` (a `Skill.ask` may return a `str` or a `Question`; `Question.voice` / `Pending.voice` say whether a spoken yes may approve it, default True). `classify(command) -> Plan` decides, and `run` classifies again from the stored string, so nothing else is trusted. **Voice or click** only when the string has no shell syntax at all (`| & ; < > ( ) $ ` { } * ? [ ] ! # \` and any non-printable character, so no newline or tab), `shlex.split` gives a bare program name in `SAFE_PROGRAMS` (`ls df du date uptime whoami pwd sw_vers hostname uname`) and its arguments pass the per-program rule (`hostname`, `whoami`, `pwd`, `uptime`: none; `date`: only arguments starting with `+` or `-`, since a bare one sets the clock); a leading `~/` is the only expansion (done by vaice, and refused in a command with quotes or a `~` elsewhere, so the argv is what a shell would have run); it runs as an argv list with no shell. Everything else is **click only** through `/bin/zsh -c`. **Why an allowlist:** a list of "read-only" program names is not read-only (`find -delete`, `sed -i`, `sort -o`, `awk` with `system()`, `xargs`, `env`, `tee`), so the voice set is tiny and argument-checked; programs that print file contents (`cat`, `head`) are click-only because their output goes to the brain. `sudo` (`\bsudo\b`, case-insensitive, anywhere in the string, quoted or not) is refused before any question: a courtesy check, not a boundary (`su"do"` passes it; the click is the boundary). The question is a fixed sentence (`ASK_VOICE` names the program only, `ASK_CLICK` names nothing; neither may hold a word of `confirm.YES`/`NO`: `tests/test_shell.py` checks them, per word, like `quit_app`'s, which is why `ASK_CLICK` avoids "that" and "it"); arguments are never read aloud. In `_decision` a click-only request is peeked with `confirmations.current()`: a spoken yes speaks `NEEDS_BUTTON` and leaves it pending, otherwise `take(pending.id)` (atomic against a click; a `None` there means the click won and the utterance is an ordinary question). Execution: own session (`start_new_session`), cwd home, stdin `DEVNULL`, stdout+stderr merged, `SHELL_TIMEOUT` 30 s, `SHELL_OUTPUT_CHARS` 20000 kept (the pipe is read to the end and the rest discarded, so a chatty child never blocks), one loop polling `select` + `stop()` + the deadline every `POLL_SECONDS` (0.05), SIGTERM to the group, `KILL_WAIT`, then SIGKILL to the group (also for a child that ignores TERM or outlives its shell); a finished command whose background child still holds the pipe is ended after `LEFTOVER_WAIT`. A background child that redirected its output (so the pipe reached EOF) is ended too, when the command exits: only the command itself is tracked, so nothing else would ever stop it. Running commands are registered in `_live` and an `atexit` hook ends them: the child has its own session, so vaice exiting would not. `Skill.run_stoppable(args, stop)` is the optional stoppable runner that `Skills.run(name, args, stop)` prefers over `run`; the voice path passes the reply's `stop` (barge-in, app stop), the click path (`AssistantResponder.approve`, on a Gradio worker) a per-run event that `clear_pending` ("New conversation") sets, plus `lifecycle.stopping`; the event is registered before `take` so a "New conversation" in between cannot miss the run. Otherwise only the 30 s end a click-approved command. After a voice-approved run `_approved` raises `_Stopped` when `stop()` is set, so a stopped command costs no brain call. The result: `speech` = `the command finished` / `failed with status N` / `was stopped after 30 seconds` / `was stopped`, then `. Output: <first 600 chars, whitespace-collapsed>` (`(more on screen)` when cut), `detail` = `$ <command>`, `(<status>)` and the raw output (the tool-event cap, 800 chars, still bounds what is stored). Tool output only ever goes into a `tool` message, never a system or user one. The panel (`app.py`) shows a `run_shell` request's command line itself (parsed with `json.loads` like the run), and for a click-only one the line `Only the Run button can approve this one; saying yes will not.`. The live eval's `stub_skills(shell=True)` drops `run_shell`'s `run_stoppable` (or the stub would run real commands) and always asks; `--shell` with `assistant_shell_cases.json`. The 2B model overcalls `run_shell` on questions about commands (first live check, one repeat), so the skill stays opt-in until the helper model. Measured on b12359 Q4_K_M (51 cases x 5): 225/255 with the skill off, 215/255 with it on; the extra failures with it on are over-calls ("Goodbye" calls `quit_app` with no name, a web-search request becomes a `curl` command), and questions about commands ("What does the ls command do?") call `run_shell`. The 2B model also writes poor commands (`/Users/me/...`, Linux `netstat` flags) and in a browser check ran a bare `ls` for "ls in my Downloads folder" and described the home listing as Downloads. That is why the skill is off by default; do not turn the default on without a better brain and a new eval.
- **Helper brain** (`brain.py`, `VAICE_BRAIN_URL` / `_MODEL` / `_API_KEY` / `_TIMEOUT`, assistant mode only): the brain can be any OpenAI-compatible endpoint; vaice does not tell local from hosted apart, and only the brain moves (transcription and `/tts` stay on the local llama-server). **URL convention:** `VAICE_BRAIN_URL` is the base URL as OpenAI clients take it, `/v1` included (`config.brain_base`: http(s) with a host, trailing slash stripped, query/fragment/credentials and a `/chat/completions` suffix refused without echoing the value, since a key may have been pasted into it); `ChatBrain` takes the full endpoint, `ChatBrain.local(url, timeout)` builds `<llama-server>/v1/chat/completions` and `ChatBrain.helper(base, ...)` builds `<base>/chat/completions`, so `/v1` is never doubled (pinned in `tests/test_brain.py`). **Body:** the helper sends `messages`, `tools` and `model` only; `temperature` and `max_tokens` are constructor choices (`None` = not sent) because hosted models differ in which they accept (some reject `temperature`, some want `max_completion_tokens`) and a cap cuts a reasoning model's answer (LM Studio's `lfm2.5-24b-a2b` spent up to 436 completion tokens on one tool call); the local brain keeps `temperature: 0`, `max_tokens: 300` because its eval numbers depend on them. **The assistant message sent back holds only `role`, `content`, `tool_calls`** (`_reply`): hosted endpoints reject unknown message fields, and `reasoning_content` (observed live with LM Studio, in a separate field) must never be replayed or spoken; `BrainReply.text` is `content` only. **Failures** are `BrainError(RuntimeError)` with a `spoken` sentence: 401/403 (message without the body, which can echo part of the key; spoken "the key was refused"), 429 ("busy"), `requests.Timeout` and any other `requests.RequestException` (wrapped, `from None`, message holds the class name only: `InvalidHeader` in requests 2.34 puts the header value into its message (`utils._validate_header_part`, `{header_part!r}`), so a key with a stray control character would be quoted, and a chained traceback would print it), other non-2xx (status + first 200 chars of the body with the key blanked), and an unusable reply (no message, malformed tool call; an extra `UNUSABLE` sentence not in the original plan). `finish_reason: length` with no content and no calls logs a warning and is an empty answer, so the caller falls back as for any empty answer. **Audible:** `_work` catches a `BrainError` from `_decision`, speaks its `spoken` sentence through the normal `/tts` path (no pending is created: `decide` never reached its end), then raises it after the frames, so `app.py` records it with `turn.fail` and the chatbot shows `<apology> (error: BrainError: …)`; raising before speaking would close the turn and drop the audio. In `_approved` (after a yes) the skill already ran, so a failed follow-up logs a warning and speaks the skill's result. The apology also lands in the turn's history like any failed reply's text (not filtered). **Key hygiene:** the key lives in `config.BRAIN_API_KEY` and the Authorization header only; no log line, message or repr holds it, startup does not even log that one is set, and the eval records the brain's host and model only (tests assert against `caplog.text`, `str`/`repr`/formatted tracebacks of the errors and the results JSON with a fake key). Startup (`app._announce_brain`) logs the host and model at INFO, warns when the model is empty, and warns when the host is not in `config.LOCAL_HOSTS`, listing what leaves the machine; chat mode with a brain URL logs one "ignored" warning; there is no startup connectivity check. **Verified:** against fakes (unit tests) and live against LM Studio (`http://localhost:1234/v1`, no key; `lfm2.5-24b-a2b`: one eval run of 4 and one of 12 cases, answer text after 2.2 s and 2.8 s median, 6.5 s max; one run per case, so no claim about call accuracy). **Not verified:** Authorization against a real endpoint, 401/403/429 bodies and any hosted provider's quirks (some reject unknown message fields or `tool_calls` shapes differently), reasoning models' behaviour beyond LM Studio's `reasoning_content`.
- **Spoken progress** (`_Progress` in `responders/assistant.py`, `VAICE_ASSISTANT_PROGRESS_SECONDS`, default 2.5, 0 = off; assistant mode only): `_work` keeps deciding inline (brain calls, skills, `_approved`'s run and its follow-up call: nothing moved), and a second daemon thread `vaice-assistant-progress` speaks `ONE_MOMENT` once the decision has taken that long (counted from the transcript, started only for a non-empty one), then `STILL_WORKING` every `PROGRESS_REPEAT_SECONDS` (12 s, counted from the end of the previous filler), through the same `_tts`, as frames with the text `""`. It polls `POLL_SECONDS` (so it honours `stop()` that fast); `_work` calls `end()` right after the decision (or the `BrainError` apology / `NOT_HEARD`) and before the `_Asked` marker and the answer's first frame, and `cancel()` in its `finally`. One lock makes "queue a filler" and "the answer starts" exclusive: the thread holds it while it queues a filler, re-checks `ended` after taking it, and `end()` sets `ended` then takes the lock once, so an answer that is ready while a filler streams waits for it, and no filler follows an answer (tested, and the test fails without the lock). **Chosen over a decision thread** (`_work` waiting on a queue, deciding elsewhere): nothing about the decision changes, so there is no abandoned decision to reason about; a reply stopped mid-decision behaves exactly as before (`_work` stays in the blocking brain call, which cannot be interrupted, then raises `_Stopped` at its next `stop()` check; the progress thread has already gone, by its own poll of `stop()`). That leaves what it always did: `_decision` may have `take`n a confirmation before `_approved` checks `stop()`, in which case the request is consumed without running (not silently run, and the next turn finds none), and `decide` raises `_Stopped` before `prepare` so a late brain reply creates no request. The filler is never recorded: its frames carry `""`, which equals the generator's initial `spoken`, so `set_assistant_text` is not called for it and history holds only the answer. **`app.py` counts the filler's seconds in `Turn.audio_handed_out`** (it counts every frame), so the barge-in text trimming is slightly generous after a filler; not restructured. The "time to first audio" log line in `app.py` is the filler's when there is one; the responder's own `assistant timings` line still reports the answer's. A `/tts` failure while speaking a filler is a warning and ends the progress for that reply. The filler's `/tts` request runs concurrently with the brain call: with the local llama-server as the brain that may compete for its slots (not measured; the local brain's ~1 s answers rarely reach 2.5 s). **Not verified:** speaker echo (the microphone hearing the filler and the VAD cutting the reply in flight, #36; headphones assumed, `0` is the off switch), and a filler in front of a real voice-approved shell command (unit tests only). Live check against LM Studio's `lfm2.5-24b-a2b` helper: with progress 0.5 s the filler was requested 0.89 s after the start and the answer at 3.03 s; with the default a 1.7–2.5 s answer got none.
- **Memory** (`memory.py`, `VAICE_ASSISTANT_MEMORY`, default off, assistant mode only; Phase 5A, #87/#8): explicit notes only, nothing is extracted in the background. `Memory(path | None)` is a thread-safe ordered list of at most `MAX_NOTES` (30) notes of at most `MAX_NOTE_CHARS` (200) characters, saved after every change as `{"version": 1, "notes": [...]}` in `<DATA_DIR>/memory.json` through `conversation.write_json_atomically` (mkstemp 0600 + `os.replace`, shared with the conversation file); no path (`VAICE_DATA_DIR=""`) = nothing read or written. - **MCP** (`mcp_skills.py`, `VAICE_MCP_CONFIG` / `VAICE_MCP_TIMEOUT`, assistant mode only, default off, optional extra `mcp` = `mcp>=2.3,<3`; Phase 5C): servers from a Claude-Desktop-shaped JSON file (`mcpServers`: `command`, `args`, `env`, `cwd`, stdio only, a `url` is a startup error) become skills `<server>__<tool>` (`[A-Za-z0-9_-]`, at most 64; MCP names hold `__` and no built-in does, so a collision with a built-in is impossible and a test pins it; two MCP skills with one name are a startup error). `app.main()` calls `_open_mcp()` in assistant mode, passes `McpTools.skills` through `AssistantResponder(extra_skills=...)` to `default_skills(extra=...)`, and closes it in `finally`; chat mode with the setting logs one "ignored" warning and never imports the SDK. **The SDK is imported only inside `mcp_skills` functions**, so config and app tests run without the extra; `tests/test_mcp_skills.py` has pure tests (fake tool objects, no process) and SDK tests behind `pytest.importorskip("mcp")` that drive `tests/fixtures/mcp_server.py` (a FastMCP-style stdio server) for real; CI installs the extra. **Policy, not the server, decides approval:** a per-server `tools` map, `run` = kind `read`, `voice` = `confirm` with a voice-approvable `Question`, `click` = `confirm` with `Question.voice=False` (the shell's click-only path: a spoken yes speaks `NEEDS_BUTTON`, the panel says only the button can approve), `auto` = `confirm` with `Question.auto_seconds` (`VAICE_ASSISTANT_AUTO_SECONDS`, default 5, 0 = the tool is built exactly like `click`); `click` is the default and a list means all click. Only listed tools are offered (unlisted: one INFO line, names only; listed but not offered: warning); annotations (`readOnlyHint`) are not trusted, at most a DEBUG log. The question is a fixed sentence naming tool and server (a generic one when either name holds a word of `confirm.YES`/`NO`, checked per word like `quit_app`'s), never the arguments. **`auto`** (`mcp_skills.auto_question`): the announcement `Using {tool} from {server} in {N} seconds.` (no answer word, per-word test, generic variant for names with one; "stop", "cancel", "it", "that" are all answer words) is a `Question(voice=True, auto_seconds=N, fallback=<the click question>)`. `decide()` swaps in `fallback` when `task.tainted` (anything ran earlier in the same task, a continuation after a spoken yes included, because its output may be untrusted page text; content read in an EARLIER turn is not tracked, the same limit every policy has), copies `auto_seconds` to `Pending`, and `_Asked(spoken=True)` carries it: when the generator arms the request it starts the daemon thread `vaice-assistant-auto` (`AssistantResponder._countdown`: polls `POLL_SECONDS`, ends when the request is no longer current, `Confirmations.remaining` is None or `lifecycle.stopping` is set, at the deadline calls `approve(pending_id)`, i.e. the atomic `take`, so a Stop click, a spoken yes/no, "New conversation" or expiry that gets there first means it runs once or never). After the run the task continues and the outcome is spoken (the assistant bullet: `_continue`, the outbox); a question that continuation ends in has no countdown of its own. The countdown counts from the announcement's ESTIMATED end of playback, because handed out is not played (TTS streams faster than real time and fastrtc's queue is unbounded): the generator keeps the estimated playback end (`_playback_end`: each frame plays after what is queued, or at once when the queue had drained, so silence between a progress filler and the answer is not counted: Codex P1 on #111), `_still_playing(play_end, now)` gives the audio still to play, `Confirmations.arm(id, playing)` stores it as `Pending.auto_delay` and `Pending.remaining` = `auto_seconds + auto_delay - elapsed` (so the panel starts above `auto_seconds`); answerability (`armed_at`) and the 60 s expiry are unchanged, and a cut-off or failed announcement is never armed, so never runs. It is an estimate (a progress filler's audio is queued like any other), not measured playback. Limit: speech still in progress when the timer fires has not been transcribed, so a spoken stop only cancels speech that has ended; the Stop button always works; the panel shows the whole seconds left (`pending_view` rounds up, one redraw a second) and the text is not spoken. **Buttons:** Gradio cannot reorder components, so `app.py` has two `gr.Row`s inside the panel, shown one at a time by `confirmation_panel` (its tuple is panel, text, id, countdown row, ordinary row, all returned by the same 1 s timer path): a request with `view["remaining"] is not None` shows **Stop** (`variant="stop"`, `responder.cancel`) then **Run now** (`responder.approve`), every other one (click-only, voice, shell, an `auto` fallback, an `auto` request not armed yet) shows **Run** then **Cancel**; the buttons do exactly what they did, only the layout changes, and the countdown text is `Runs by itself in N s; press Stop to cancel it.` (the live check below used the earlier Cancel button) The model can never make a tool looser: the tier comes from the config only (step 2, not built: the model may flag a call as risky to drop it to click-only). Verified by unit tests with fakes only (a fake clock and one real-time run); not tried live with a real browser MCP server. **Untrusted input:** the description (the brain reads it; this is the prompt-injection door) is one line, control characters removed, 300 characters, prefixed `(from <server>)`, and the schema's own `description` strings are cleaned the same way; the `input_schema` is otherwise passed through (its `default`/`enum` strings are not cleaned). A result is a `tool` message only; speech is capped at 2000 characters with `(more on screen)`, the detail keeps the raw text; `is_error` is a `SkillError` (spoken), an empty result says `the tool returned nothing`, an embedded text resource is spoken as its text. **One asyncio loop on a daemon thread** (`vaice-mcp`) with one long-lived task per server, because the SDK's anyio cancel scopes must be entered and left by the same task (`mcp.Client` as an async context manager: leaving it closes stdin, terminates, kills). A call (`run_stoppable`, also a plain `run`) is `run_coroutine_threadsafe` plus a poll of `stop()` and the deadline every `POLL_SECONDS` (0.05), cancelling the future on stop or timeout (the SDK's per-call timeout is `VAICE_MCP_TIMEOUT`, with `CALL_GRACE` 1 s as vaice's own backstop). A server that does not start in the timeout is skipped with a warning; `close()` is idempotent and has an `atexit` backstop it unregisters. **Secrets:** `env` values are never logged or put in an error (validation names the server and the key, not the value; a test greps logs, messages and tracebacks for a fake token); the child's stderr goes to `<DATA_DIR>/mcp-<name>.log` (0600, a temp dir when `DATA_DIR` is None), not the terminal; a leading `~/` in `args`, `env` values and `cwd` is expanded by vaice. A missing `tools` key offers nothing (INFO). Unknown keys in a server entry are an error (`type: "stdio"` is accepted). **Verified:** against the real SDK and a real child (round trip, tool error, empty result, stop, timeout, a call the server never answers, `close()` leaves no process, startup timeout, the `env` reaching the child). **`auto` verified live (2026-11-17, headless test Chrome as the microphone, a spoken clip, Omni Q8_0, a headless Chrome DevTools server):** the announcement ("Using new page from chrome in 5 seconds.") was spoken, the panel counted down from 8 s (5 plus about 3 s of estimated playback; a first run with a longer, two-sentence announcement counted from 12 s, hence the short sentence), the call ran once at 0, and **Cancel** two seconds into another countdown ended it with `cancelled` and no run. ## Gotchas (each has bitten this repo)

- **fastrtc threading:** fastrtc resumes the reply generator on a different worker thread for each chunk. When testing code that runs inside a framework executor, reproduce this real threading (fresh thread per resume) and confirm the test fails against known-bad code first; a harness that called `emit()` from one thread passed while the live app failed. The one shared harness lives in `tests/threads.py` — no per-file copies.
- **The stop signal:** gradio installs no SIGINT handler of its own (`gradio/http_server.py:47 install_signal_handlers` is `pass`; its uvicorn server runs in a daemon thread and `uvicorn/server.py:332 capture_signals` only listens on the main thread), so `lifecycle.py:install_stop_handler()` stays in charge: Ctrl+C sets `lifecycle.stopping` and raises `KeyboardInterrupt`, which gradio's `block_thread` (`gradio/blocks.py:3044`) turns into `server.close()`. The responder polls the flag while it waits for the server and returns without a reply.
- **fastrtc's idle polling:** `player_worker_decode` (`utils.py`) loops `await loop.run_in_executor(None, handler.emit)` as fast as the executor can schedule it, so an idle connection burned ~64% of a core (~32k `emit()` calls/s, measured). `InterruptSafeReplyOnPause.emit()` waits for the pause event (`self.event.wait(timeout=IDLE_WAIT_SECONDS)`) instead of returning None at once: ~37 calls/s, ~1% of a core. The wait ends as soon as the event is set, so no latency is added — and `emit()` runs in a worker thread (the asyncio default executor in the WebRTC path, an anyio worker thread in the websocket path), never on the event loop.
- **Single connection:** fastrtc's `Stream` defaults to `concurrency_limit=1`, so a second WebRTC connection is refused (`concurrency_limit_reached`), not queued. A page reload is not affected (Chrome closes the old peer connection on navigation, so the slot is free within ms; measured), but a connection the browser never closes (tab force-closed, browser closed, measured headless via Playwright) holds the slot ~30 s until aioice's consent checks expire (6 failures x ~5 s). The reload console errors `BodyStreamBuffer was aborted` / `Connection errored out` come from Gradio's JS client when the navigation cuts its open `queue/data` event stream (the only request in flight at reload); harmless, and never seen without the chatbot/`additional_outputs`. Barge-in: fastrtc's `close()` on the reply generator fails ("generator already executing") because `emit()` is mid-`next()` on another thread; the reply actually stops when CPython finalizes the dropped generator. The `next()` that was in flight still returns a chunk, which fastrtc would queue after clearing and play; `interruptible.py:InterruptSafeReplyOnPause` (what `app.py` uses) drops it by noticing that `receive()` replaced `self.generator` while `emit()` ran. It relies on fastrtc 0.0.34 internals (`generator` is set to None on interrupt; `copy()` must be overridden because fastrtc copies the handler per connection — `interruptible.py:copy()` passes every argument by keyword and `_copy_kwargs()` is checked against `ReplyOnPause.__init__`'s signature in `tests/test_interruptible.py`, so a fastrtc release that adds, drops or reorders a parameter fails there instead of silently misplacing a value), and `tests/test_interruptible.py` drives the real `ReplyOnPause` so a fastrtc upgrade that changes this fails there. A chunk handed to fastrtc just before the interrupt still plays. The other half of the same race (#13): if the reply's last `next()` raises `StopIteration` while the barge-in pause is pending, plain `ReplyOnPause.emit()` calls `reset()`, which clears the event and replaces the state — wiping the pause and audio `receive()` had just accumulated, so the interrupting question is silently lost; `InterruptSafeReplyOnPause.emit()` snapshots the state before `super().emit()` and restores event + state when that reset wiped a detected pause. The restore only fires for true end-of-reply cleanup: a `reset()` override counts resets on the emit thread (fastrtc's own) vs other threads (`stop_playing_reply`, `clean_up`) and an explicit reset during the call is never undone; `receive()` and the check share a lock, and the restore also stands down when the event is re-set or the fresh state already holds collected audio (`stream`/`buffer` non-None — a newer utterance wins); and it only fires when emit began with a reply generator attached — if super() had begun the reply from the pause itself, re-arming it would let an empty reply loop forever. Replies are capped at 1024 tokens (text + audio frames); truncation is logged. On barge-in (fastrtc acts when the interrupting utterance *ends*), the next `start_turn()` freezes the old turn, so a late finalization can't change history, and cuts its text to the share of audio that could have played since the first chunk (handed out ≠ played: fastrtc's playback queue is unbounded). LFM's interleaved text runs ~2x ahead of its audio, so the text is split by the share of audio generated (`base.spoken_part`).
- **Proactive speech: the outbox, served by the idle `emit()`** (`outbox.py`, `interruptible.py`; #110): a spike showed fastrtc plays whatever an idle `emit()` returns, so speech with no reply generator (the outcome of a click- or auto-approved call, `AssistantResponder._continue`) is queued on an `Outbox` (thread-safe FIFO of audio frames `(rate, float32)` and `Marker(callback, on_drop)`s) that `InterruptSafeReplyOnPause(outbox=...)` serves; `copy()` gives every connection's copy the same outbox (set on the copy, NOT in `_copy_kwargs()`, which `tests/test_interruptible.py` pins to `ReplyOnPause.__init__`). **Serving is paced, which is essential:** fastrtc's playback queue is unbounded and `emit()` runs ~37 times a second, so serving at once would queue a whole outcome in a fraction of a second, fire the markers long before playback, make a later clear find nothing and arm a question before it played. So the idle `emit()` (after its wait: no pause pending, `generator is None`, `not state.started_talking`) polls the outbox and serves the next item (a frame, or a marker whose callback runs on the emit thread, wrapped, and the loop goes on in the same call) only while `_proactive_until` (the estimated end of the audio served so far, extended by `len(samples)/rate` per frame, **reply audio included** (`_note_playing`: a click while the question is still playing finds its audio queued ahead, so the outcome waits behind it; Codex P2 on #115; speech over a running reply resets it, because fastrtc then drops that audio), under its own lock because emit runs on a different worker thread per call) is less than `LEAD_SECONDS` (0.4) ahead of now: markers fire within that lead of real playback (recorded text, arming a question). **Speech start** (`receive()`, where `started_talking` flips, outside `_state_lock`): with no reply generator and `can_interrupt` (off: speech never clears proactive audio, as on the reply path) the outbox is cleared (the markers' `on_drop`s run) and, only if proactive audio is estimated still playing, fastrtc's `_clear_queue` is called (the call fastrtc's own `receive()` makes on a pause); with a reply generator running the existing barge-in handles it and the outbox is untouched. `stop_playing_reply` ("New conversation") clears it too. **Staleness is not item age** (a long outcome waits behind its own playback) but no connection draining: every `emit()` call (a reply running included) is a poll or `touch()`, and a gap of more than `STALE_SECONDS` (30) since the previous one, or none yet, clears the outbox first (running the `on_drop`s): speech queued while nobody's connection was polling must not play on a later one. The heartbeat on every `emit()` (not only idle ones) is deliberate: a reply longer than 30 s would otherwise make the next outcome look stale. Outbox callbacks and drop hooks run outside its lock; a failing one is logged, never raised. **Cancel vs the queue:** each `clear()` starts a new outbox `generation`; the continuation's `_OutboxSink` captures it at the start and `put`/`put_marker` refuse a stale one (a refused marker runs its `on_drop` at once), `_continue` checks `stop()` after `_speak` returns (a cancel that lands while the last `/tts` stream is closing, past `_tts`'s per-chunk check), so a cancelled and cleared task queues no further frame, sentence marker or arming marker. What remains: a frame queued just BEFORE a clear is cleared with it as intended, but a frame already handed to fastrtc by the idle `emit()` before the speech-start clear plays out (the `_clear_queue` call covers it only while the proactive audio is estimated still playing, and fastrtc's queue clear is best effort). **Not verified live** (unit tests with a fake clock drive the real `ReplyOnPause`; the playback itself, concealed-sample gaps and speech start mid-outcome in a browser are checked separately by hand).
- **fastrtc's VAD defaults & pre-roll:** `fastrtc` 0.0.34's default `SileroVadOptions` uses `min_silence_duration_ms=2000` and `speech_pad_ms=400` inside `AlgoOptions.audio_chunk_duration=0.6` (600 ms) chunks. Because `2000 ms > 600 ms`, Silero never closes a triggered segment inside a chunk and `silero.py:235` counts trailing silence as speech, inflating a 180 ms noise burst into 600 ms of speech (`dur_vad = 0.6s > started_talking_threshold`). Conversely, speech starting in the last ~250 ms of a 600 ms chunk is discarded when `determine_pause()` sets `state.buffer = None`, clipping opening words ("What is…"). `InterruptSafeReplyOnPause` defaults `model_options` to `DEFAULT_VAD_OPTIONS` — built from `config` (`threshold=0.6`, `min_silence_duration_ms=150`, `speech_pad_ms=30`; env-tunable via `VAICE_VAD_THRESHOLD`, `VAICE_VAD_MIN_SILENCE_MS`, `VAICE_VAD_SPEECH_PAD_MS`, with `VAICE_CAN_INTERRUPT` wiring fastrtc's `can_interrupt`) — and keeps a `PREROLL_SECONDS = 0.3` pre-roll tail on `AppState` from the last discarded pre-speech chunk, prepending it to `state.stream` when `started_talking` flips to `True`.
- **llama-server realtime: history is ChatML in `instructions`, one fresh session per reply:** `conversation.item.create` with the assistant role is rejected ("only user messages and function call outputs are supported"), so earlier turns can't be replayed as items. `llama-server` wraps `instructions` in `<|im_start|>system\n...\n<|im_end|>\n<|im_start|>user\n` and tokenizes the header with `parse_special=true` (`server-realtime.cpp:1122`), so `_instructions()` closes the system block and formats each past turn as `<|im_end|>\n<|im_start|>{role}\n...` (stripping any control/placeholder tokens from turn text). That gives LFM3-Audio native multi-turn ChatML tokens instead of a flat `User:` / `Assistant:` transcript inside the system prompt (which caused role mix-ups and self-reinforcing repetition loops in 2B models) while keeping `conversation.py` the single owner of history (windowing, barge-in cuts, "New conversation").
- **llama-server realtime: no user transcript in a conversation session:** the transcript comes from a second session (`session.update` type `transcription`, no language so the model detects it: `common/chat.cpp` maps an empty language to "Perform ASR.", `audio.input.transcription.language` pins one), the same PCM, `input_audio_buffer.commit` → `conversation.item.input_audio_transcription.completed`. It runs in parallel with the reply (the server has several slots), so it is usually done before the reply ends.
- **llama-server realtime: rates and truncation:** the sample rates come from `session.created` (`audio.input.format.rate`, `audio.output.format.rate`), never hardcoded; `turn_detection` is null (fastrtc's VAD decides). A reply cut off by `max_output_tokens` still reports `response.done` status `completed`; only `usage.output_tokens >= max` shows it (`server-realtime.cpp`: `n_decoded >= n_predict`). The cap is `VAICE_LLAMACPP_MAX_OUTPUT_TOKENS` (default 1024, the model card's voice-chat example; 512 truncated most 1–2 sentence replies — the LFM3-Audio codec emits 12 tokens per 80 ms of speech, so text + audio tokens add up fast). Closing the socket mid-reply cancels the server task and frees the slot, and the next session is unaffected; `/v1/models` reports the model's outputs under `data[].architecture.output_modalities`.
- **llama-server realtime: do NOT pin language/voice for voice chat:** `--tts-lang`/`--tts-voice` (or per-session `session.update` → `audio.output.language`/`audio.output.voice`, llama.cpp PR #31982, 2026-11-10 — newer than v0.8.0) make llama.cpp render a `Speak in <Language> [using a <voice> voice].` line into the system prompt for LFM3 templates (`common_chat_get_speech_system_prompt` + `configure()` in server-realtime.cpp, prepended to the client's instructions). An early single-session repro (b12359, `Q8_0 --temp 0`) blamed that line for parroting; a controlled re-test on the **same build** (flags, per-session `audio.output.*`, and the line injected into `instructions` by hand; clean `say`-generated TTS and noisy real-mic inputs) did **not** reproduce the parroting in any configuration — the flags are unnecessary for an English-only voice model, not a proven echo cause. With the line injected + noisy mic input, one reply degraded into a rambling run-on. Voice-chat mode prefills `<|mixed_start|>` (not the `<|think|>` prefill that text-only reasoning uses), so interleaved replies never reason — `--reasoning off` is an LFM3-Omni concern, not Audio. The *transcription* language also stays auto-detect: pinned `language=en` ASR measurably repeats the passage (audio.cpp port: 4.3–4.4% WER vs 0.07–0.14% with auto). Echo turns that land in `conversation.json` self-reinforce as ChatML `user: X → assistant: X` pairs; the fix is clearing the history (and `--temp 0`).
- **llama-server realtime: text temperature is a server setting, not a client one:** `session.update` and `response.create` take no temperature (`server-realtime.cpp` parses only instructions/modalities/tools/max_output_tokens), so reply text is sampled with llama-server's launch-time sampling params (default 0.8). The LFM3-Audio model card recommends greedy decoding for text (`--temp 0`); at 0.8 a 2B audio model drifts off-topic and loses the thread, while speech stays fluent (audio sampling params come from the GGUF and are applied by the gen-audio pipeline). `check_server()` reads `/props` (`default_generation_settings.params.temperature`) and warns; a router-style `/props` with no params, or a failed fetch, logs a distinct hint ("could not verify the server's temperature — start llama-server with --temp 0") so an absent warning is never mistaken for `--temp 0` being set.
- **llama-server realtime: tools are the server's built-ins, declared flat, required first:** `session.update` takes `tools` in the **Responses API flat format** (`{"type": "function", "name", "description", "parameters"}`) — the chat-completions nesting gets re-nested by `server_chat_convert_responses_tools` and rejected ("key 'name' not found"). The server's built-in tools (enabled with `--tools`, experimental) are listed by `GET /tools` (chat-completions nesting, needs flattening) and executed by `POST /tools` with `{"tool": name, "params": <json-object>}`. The key is `params`, not `arguments`: the server reads the tool's parameters from an object, so the model's `arguments` JSON string is parsed first. Passing the string as `arguments` leaves `read_file` without its `path` (the server answers `key 'path' not found`) while parameterless tools such as `get_info` work by accident. The model's calls arrive as `response.output_item.added` (type `function_call`, with `item_id`/`name`/`call_id`) + `response.function_call_arguments.delta`, and the results go back as `conversation.item.create` `function_call_output` items before the next `response.create` — the model then speaks the answer, and the session survives the round. Live-validated behavior of LFM3-Audio 2B: `tool_choice: "required"` with 1–2 tools is reliable **in text-only mode** and does NOT fire on ordinary questions, but it is not enforced with `output_modalities: ["text","audio"]` — a voice question can be answered without a call, so the prompt and the tool subset decide in practice; `"auto"` announces a check and stops without calling; 3+ tools answer from the model's head (hallucinated "Linux" on macOS). A bare follow-up `response.create` inherits the session's `required`, so after a tool result the model called again, repeated/leaked the raw result and could loop to the token cap; `_create_response` therefore overrides each follow-up with `auto`, and with `none` at `MAX_TOOL_ROUNDS` (2) to force the answer (a call in that forced round is ignored and logged). The call rate depends on the prompt: with the default "Reply naturally and concisely…" prompt the model calls in ~1 of 6 runs; a prompt telling it to use the tools ("Use the available tools to answer questions about this system.") made it 4 of 4 — document the prompt knob, don't force text into the user's prompt. Text deltas around a tool round leak the raw result and stray `</answer>`/`</think` markers (the `_MarkupStripper` drops `<tool_call>…</tool_call>` blocks, orphan `</think` fragments, `<|…|>` control tokens and `<answer>` delimiters — across deltas, holding back partial tags; an unterminated block is dropped entirely); recorded and displayed text is kept free of that markup. Tool rounds are capped (`MAX_TOOL_ROUNDS`); the executor runs on the session thread, must never raise (failures are spoken), and checks `stop()` between calls. The model **reads the fed-back tool result aloud** (a 2B-model limitation; prompt lines forbidding it have no measurable effect), so the result is compacted first (`_speech_friendly`: JSON → short `key: value` pairs, values truncated at `TOOL_VALUE_CHARS`=200, whole output capped at `TOOL_OUTPUT_CHARS`=800, both env-tunable) — the first spoken sentence answers, the dictation that follows stays short. A read_file payload (`plain_text_response`) is the exception: the per-value cap cut the last word of a 210-char file at 200, so it is bounded by the whole-output cap instead. The old 40/120 caps cut answer-bearing data: `get_info`'s OS build string lost its timestamp before the model could speak it. Tool calls are reported to the `Turn` (`add_tool_event`, persisted as `tools`) **by the session thread itself** (a consumer drain lost calls that finished after barge-in — three Codex findings) and shown in the UI's collapsed *Tool activity* panel, never in the conversation (each result is recorded and rendered capped at 800 chars with a `... (truncated)` marker). The tool set is the server's `--tools` decision: `GET /tools` lists what it advertises, `POST /tools` refuses what it does not (live-verified 404), so `fetch_tools` takes everything and there is no client-side filter or guard — `VAICE_LLAMACPP_TOOLS` is on/off (`builtin`). `write_capable_tools` reads the same listing's `permissions.write` so startup can warn when the server advertises `exec_shell_command`/`write_file`/`edit_file` (a live voice demo on `--tools all` called `exec_shell_command` with `ls -la`). See `tasks/repro_tools.py` for the experiment.
- **llama-server realtime: the clock line is imperative, because the declarative version misfired — and prohibition-heavy lines broke the audio:** every reply's instructions carry `You know the current date and time: … Use it when asked about the date or time.` (built per reply). A bare declarative `Current date and time: …` was read as inert text: the model echoed it verbatim and still answered *I don't have access* (live, 3/3 runs). The imperative wording answered with the real time 6/6 on the same build. A prohibition-heavy *grounding* line ("the result is data, not the answer" + "do not read the raw result aloud") measurably broke interleaving: ~1 in 3 tool-question follow-up rounds came back as short text with ~2 tiny audio deltas (`usage.output_tokens == 20`, ≈0.2 s of cough) — a spoken-nothing answer, worst on `--temp 0`. Rewordings without the prohibition behaved exactly like no line (0/12 terse-silent). The line was dropped, tracked in #77; don't re-add a prompt line without a live A/B, and don't type a prompt line that forbids and expect the audio to survive it.
- **llama-server realtime: text before a tool result is working out loud; loops are cut after the answer:** at each tool-round boundary the session thread starts a fresh accumulator (`acc = [text, samples]`) and pushes a `_ROUND` marker through the consumer queue ahead of this round's frames; every frame carries a **live reference to its own round's accumulator** (not a snapshot — the consumer reads it at its own pace, and a preamble frame dequeued after the thread raced into the next round still pairs with that round's final samples), so only the final round's text is recorded and `spoken_part` is measured against that round's audio on both sides (the `Turn` barge-in cut stays reply-wide — accepted approximation). The preamble is spoken but never reaches the record. A reply whose text repeats the same 1–4-line block 3× back-to-back is cut there: the repeated tail is trimmed from the record, the session's socket is closed, and the server slot is freed — otherwise greedy decoding loops such a reply to the token cap (seconds of junk audio). The detector is line-based and comparison is normalized (case and punctuation ignored); while streaming only **completed lines** are compared (a third "Status: ready" that is becoming "Status: ready for input" is not a loop) and the final line is checked when `response.done` arrives — so a loop whose last line has no trailing newline is still trimmed from the record; 3 repeats is the bar (2 is a refrain, not a loop), single-line repetition inside one line is not detected, and if the whole reply is the loop one copy is kept so the turn still knows the answer.
- **llamacpp threading:** the `websockets` sync client is not tied to a thread (`sync/connection.py`: sequential `recv()` from different threads works, only concurrent calls raise `ConcurrencyError`; its I/O and keep-alive threads are daemons), but `connect()` blocks for `open_timeout` and `close()` for `close_timeout`, and fastrtc's executor threads are joined at exit. So each session's socket lives on a daemon thread of its own, which never holds the responder directly, and the generator only polls a queue (`POLL_SECONDS`) for `lifecycle.stopping` and `turn.closed`; its `finally` sets the cancel event and the session thread closes the socket. The close itself runs on one more daemon thread (`_open`'s exit): llama-server (b12359) does not complete the close handshake, so `close()` waits out `CLOSE_TIMEOUT` (1 s), and waiting for it reported every transcript and every reply's end 1 s late (#90, measured: transcript 0.17 s vs 1.17 s; reply end 0.00 s vs 1.00 s after the last frame). The close frame is sent at once, so the server still frees the slot. `ping_interval=None`: the idle timeout (`VAICE_LLAMACPP_TIMEOUT`) already covers a silent server.
- **Input audio:** llama-server's realtime endpoint wants PCM16 mono at exactly the session's input rate (16 kHz for LFM3-Audio), so `audio.to_pcm16` resamples the browser's 48 kHz audio with `scipy.signal.resample_poly`.
- **A reply error must not escape the generator:** fastrtc wraps the per-connection `emit()` in `webrtc_error_handler` (`webrtc_connection_mixin.py`), so an error that escapes the reply generator comes back as a `WebRTCError`, which the player loop re-raises (`utils.py: player_worker_decode`) — the connection's audio task dies and the page stays mute until a reload. `app.py` therefore catches the error inside the generator, records it on the turn and shows it in the chatbot (`tests/test_interruptible.py` pins both halves); even reading the state back for the UI is guarded, so the generator itself never raises. `conversation.py:_save()` treats a failed write as a warning: the conversation continues in memory and is lost when the app stops.
- **Gradio's `allow_tags` warning:** gradio 5.50 warns that `gr.Chatbot(allow_tags)` will default to `True` in 6.0 *even when you pass `False` explicitly*, so the warning cannot be silenced. Keep `allow_tags=False` in `app.py` anyway, so the upgrade does not start rendering the model's text as HTML.

## Repo conventions

- `tasks/` is local-only and gitignored: `tasks/todo.md` holds the plan/review notes for the current change; `tasks/lessons.md` records lessons after user corrections. Read `lessons.md` at session start if it exists.
- The llamacpp backend is tested against llama.cpp `llama-server` (b11960+) only; keep `responders/llamacpp.py` and the docs honest about that (see `docs/installation.md`, "Requirements").
- Behavior/config changes must update the matching page in `docs/` in the same change (an env var: `docs/configuration.md`; how the pieces fit or the code layout: `docs/architecture.md`; a roadmap item landing: `docs/vision.md`), and `README.md` only when the quickstart or the feature list changes. Adding, removing or re-defaulting a `VAICE_*` variable also updates `.env.example`.
