## [Unreleased]

### Fixed
- **A call that asked for confirmation was shown to the model twice, so it sent every call twice** (assistant mode; a confirm skill and every `auto` MCP tool). Such a call is stored as two events, `waiting for confirmation` and then its result (or `cancelled`, `not confirmed`, `expired`), both with the same name and arguments; once real arguments were replayed (below) the model saw the same call twice in one assistant message and copied the pair (`take_snapshot` x2, `navigate_page` x2 in a real LM Studio request log). The history now leaves the wait out when a later event of the same turn has the same name and arguments; a call that is still waiting keeps its one entry. Only what is replayed to the model changes (old saved conversations included): the stored events, `conversation.json` and the *Tool activity* panel are as before. The literal is now `conversation.WAITING_FOR_CONFIRMATION`.
- **A replayed tool call lost its arguments** (assistant mode). History put every earlier skill call back as `{}` although the real arguments were stored, and the model imitated it: on a real session the 24B helper brain left the required `pageId` out of `chrome__take_snapshot` on most calls (1 of 8 first replies carried it with `{}` replayed, 8 of 8 with the real arguments). A replayed call now carries its stored arguments, as compact JSON when they form a JSON object of at most 300 characters (new `TOOL_HISTORY_ARGUMENT_CHARS`); anything else, a longer object included, replays as `{}`, never cut off (invalid JSON is rejected by hosted endpoints). A history entry that carries arguments is a JSON object `{"name", "arguments", "output"}` (`conversation.tool_entry`); the plain `name: output` entry still works and replays as `{}`. Chat mode, `conversation.json` and the local brain's request body are unchanged. Eval cases can carry a tool entry's arguments (`evals/README.md`), and the five cases with a replayed call now do.
- **"I'm unable to see the screen right now" on a busy screen** (`look_at_screen`). The vision request had no length limit and the model described the whole screen: 400 to 830 tokens (5 to 9 s) on a real desktop, and once a 2600-token run-on that reached `VAICE_VISION_TIMEOUT` (30 s) and was spoken as "I can't reach my vision model". The request now carries `max_tokens` (new `VAICE_VISION_MAX_TOKENS`, default 200; `0` sends none) and the vision system prompt asks for one or two short sentences: median 112 tokens and 1.8 s on the same screen, none at the cap (8 runs; the old prompt reached the cap in 6 of 8, 2.7 s).
- **"What do you see now?" answered from the earlier screen answer** instead of taking a new screenshot (assistant mode, `look_at_screen`). The model answered from the conversation history without calling the skill (replaying a real conversation: 0 of 5 looked again). The default assistant prompt now says the screen, battery, disk and other live facts change so the tool must be used again, and the skill's description says every call takes a new screenshot; the same replay then looks again 5 of 5. Eval cases can carry their own `history`, and three follow-up cases were added (plus two for the battery: `battery-again` still misses, 0/5).

### Changed
- **Assistant mode: a task step budget instead of three brain calls per reply** (`VAICE_ASSISTANT_MAX_STEPS`, default 10; `VAICE_ASSISTANT_TASK_SECONDS`, default 120). The fixed limit of three is gone: the brain may call skills until it answers, and the call that leaves no step, or finds the time used up, is made without tools so it must answer (the time is checked between calls; one in flight is not cut off). Multi-step work (list pages, take a snapshot, read, answer) no longer hits the third call. Whether a skill has run (which makes an `auto` MCP call ask for the Run button and makes `remember` refuse) now belongs to the task, not to one brain loop. A click or an `auto` run still only runs the call; the brain does not go on after them yet (#110).
- **A Stop button while an `auto` countdown runs** (assistant mode, MCP `auto` policy). The panel of a request that runs by itself showed the same **Run** (highlighted) and **Cancel** as an ordinary "approve this" prompt. While the countdown runs it now shows the red **Stop** button first and **Run now** beside it, and the text reads "Runs by itself in N s; press Stop to cancel it."; **Stop** cancels and **Run now** approves exactly as **Cancel** and **Run** did. Every other request (click-only, voice, shell, an `auto` request that fell back to click or is not armed yet) keeps **Run** and **Cancel**. Layout only: two button rows toggled together with the panel by the existing 1 s timer.
- **Default model is now LFM3-Omni-2B `Q8_0`** (`VAICE_LLAMACPP_MODEL`, was LFM3-Audio-2B `Q4_K_M`): it speaks, listens and reads images, so one server can serve chat mode, assistant mode and `look_at_screen`. The download is about 2.4 GB (4 GB of memory loaded, was about 1 GB). On the 51 assistant cases it scored 250/255 against 225/255 for the old default; chat mode and assistant mode were checked in a browser. Memory, shell and vision stay off by default because each costs points on ordinary requests (measured numbers in AGENTS.md). Set `VAICE_LLAMACPP_MODEL=LiquidAI/LFM3-Audio-2B-GGUF:Q4_K_M` for the old one.
- **Docs: the Jarvis name is explained** (J.A.R.V.I.S., the AI in the *Iron Man* films) in the README and `docs/vision.md`.
- **Documentation moved into `docs/`.** The README is now a short overview with a quickstart; the rest of it lives in `docs/` (installation, configuration, chat mode, assistant mode, helper model, screen vision, MCP tools, conversation, privacy, troubleshooting, development), indexed by `docs/README.md`. New: `docs/architecture.md` (the processes, both modes, the confirmation and safety model, threading, state on disk and the code map) and `docs/vision.md` (the north star, principles, where the project is and what is missing). The text of the moved sections is unchanged apart from links and headings; messages and comments that named a README section now name the `docs/` page.
- **Python 3.12 only** (`requires-python = ">=3.12,<3.13"`, was 3.10–3.12): 3.10 reached end of life in October 2026, 3.11 was never tested, and `uv sync` downloads 3.12 from `.python-version` when it is missing. Installing on 3.10 or 3.11 now fails with a clear version error. The 3.10-only `onnxruntime<1.24` bound is gone. CI runs one macOS job instead of two, and a newer push to a pull request cancels the older run (`concurrency`), so fewer jobs wait for a macOS runner (#91).
- CI can be started by hand (`workflow_dispatch`: Actions > CI > Run workflow, or `gh workflow run ci.yml --ref main`), for a push whose run never started: #104's merge hit a GitHub 502 and reached `main` with no CI run.

### Added
- **A click or an `auto` run now continues the task and speaks the outcome** (assistant mode, #110). After **Run** or an `auto` countdown the call ran and nothing else happened: the brain was not asked and nothing was said. It now continues the task as it does after a spoken yes (same step budget, the approved result taints the task so an `auto` tool falls back to a click, `remember` is refused), and the outcome (an answer, or another confirmation question) is spoken with no reply in flight, through a new `Outbox` that the audio handler's idle `emit()` serves, paced by the estimated end of playback. The spoken text is added to the asking turn's chat bubble as its audio is served; starting to talk, a new reply, a second approval or *New conversation* cancels it. A question it ends in is shown at once and can be answered only once it was spoken, without a countdown. Covered by unit tests with fakes; the real audio path is checked by hand.
- **The brain goes on after a spoken yes** (assistant mode). After an approved call the brain was called once, without tools, to say how it went. It now continues the same task with tools: it may call more skills (the step budget keeps counting, and the approved call's result taints the task) or ask another question, which is spoken and waits like any other. An empty answer, or a brain failure after the call ran, speaks the approved call's own result. Settings `VAICE_ASSISTANT_MAX_STEPS` and `VAICE_ASSISTANT_TASK_SECONDS`: `docs/configuration.md`, `.env.example`. Verified by unit tests with fakes only; not tried live.
- **`auto` policy for MCP tools** (`"auto"` in a server's `tools` map; `VAICE_ASSISTANT_AUTO_SECONDS`, default 5, `0` = off, assistant mode only): between `voice` and `click`, a stop button with a timer. The assistant announces the call ("Using navigate page from chrome in 5 seconds.", a fixed sentence naming the tool and the server, with none of the words you answer with), the panel shows the exact call with a countdown and a **Stop** button (with **Run now** beside it), and the call runs by itself when the time is up unless you press **Stop**, say stop, cancel or no, or say anything else (it is then dropped); a spoken yes or **Run now** runs it at once. The countdown runs from the estimated end of the announcement's playback (audio handed out minus time since the first frame; an estimate, not a measured position) and starts only when the whole announcement was handed out, so a cut-off announcement never runs; speech still in progress when it fires has not been heard yet (the **Stop** button always works); the timer goes through the same atomic take as the buttons, so a call runs at most once. If any other skill ran earlier in the same reply, an `auto` call is asked as a `click` one (that skill's output may be untrusted text); content read in an earlier turn is not tracked. The policy comes from the config only, and with the setting at `0` an `auto` tool is built exactly like `click`. Verified by unit tests with fakes (fake clock, one real-time run, a cancel landing between the timer's check and its run); not tried live with a real MCP server. Docs: `docs/mcp-tools.md`, `docs/configuration.md`, `docs/assistant-mode.md`, `docs/architecture.md`, `.env.example`.
- Assistant mode MCP tools (#87; `VAICE_MCP_CONFIG`, `VAICE_MCP_TIMEOUT`, off by default, assistant mode only, behind the optional extra `mcp`: `uv sync --extra mcp`, `mcp>=2.3,<3`): vaice starts the stdio MCP servers named in a JSON file (Claude Desktop's `mcpServers` shape: `command`, `args`, `env`, `cwd`; a `url` entry is an error) and offers the tools you list as skills called `<server>__<tool>`. A `tools` key per server sets each tool's approval: `"run"` (runs at once), `"voice"` (a spoken yes or the **Run** button) or `"click"` (only the **Run** button; the default, and what a plain list means). Only listed tools are offered and a server's own annotations are not trusted. The confirmation question is a fixed sentence naming the tool and the server, never the arguments. A tool's description is cleaned (one line, no control characters, 300 characters, prefixed `(from <server>)`) and a result is spoken up to 2000 characters, kept whole in the *Tool activity* detail, and reaches the brain only as a tool result; `remember` refuses once such a skill ran in the reply. Servers run on one asyncio thread (`vaice-mcp`), a call stops on barge-in, *New conversation* and app stop and ends after `VAICE_MCP_TIMEOUT`, a server that does not start in that time is skipped with a warning, and every child is ended when vaice stops. A server's stderr goes to `<VAICE_DATA_DIR>/mcp-<name>.log` (mode 0600). A bad file exits with `vaice: VAICE_MCP_CONFIG: ...` naming the server and never an `env` value; startup logs one line per server with tool names only; chat mode with the setting logs one "ignored" warning. With the setting on and the package missing, vaice exits with the install command. New: `mcp_skills.py`, `default_skills(extra=...)`, `AssistantResponder(extra_skills=...)`. CI now installs the extra, so the SDK tests (a stdio fixture server in `tests/fixtures/`) run there and skip without it. Verified against fakes and a real stdio server over the SDK (start, call, tool error, empty result, stop, timeout, shutdown); not verified: any real-world server, remote servers (unsupported), reconnecting after a server dies, and how well the 2B brain picks among many MCP tools (no eval).
- Assistant mode vision (#87; `VAICE_VISION_URL`, off by default, assistant mode only): a `look_at_screen(question)` read skill. When you ask about your screen ("What's on my screen?", "Read the error message"), vaice takes one screenshot of the main display (`screencapture -x -m`, shrunk with `sips` to at most 1024 px on the long edge, JPEG) in a private temporary directory, sends it with your question to a vision model, deletes it right after, and speaks the model's short answer (markdown emphasis removed, cut at 600 characters); the answer reaches the brain as a skill result. The vision model is any OpenAI-compatible endpoint that accepts images (LFM3-Omni-2B on a `llama-server` of its own, or a hosted model), set with `VAICE_VISION_URL` (base URL, `/v1` included, validated like `VAICE_BRAIN_URL`), `VAICE_VISION_MODEL`, `VAICE_VISION_API_KEY` (a secret: only in the `Authorization` header, never logged) and `VAICE_VISION_TIMEOUT` (default 30 s). Without Screen Recording permission for the app that runs vaice (your terminal) the assistant says how to grant it and to restart that app. The vision model is told that text in the image is content, not instructions, and `remember` still refuses once another skill ran in the reply, so text read off the screen cannot become a note. Startup logs the vision host and model and warns when the host is not local, since a screenshot of your screen goes there; a screenshot is taken only when the skill runs and neither its bytes nor the key are logged. A failing vision endpoint is spoken like a failing brain, naming the vision model. New: `vision.py`, `default_skills(vision=...)`, `AssistantResponder(vision=...)`; `config.brain_base` names the matching `..._API_KEY` variable in its credentials error. Verified against fakes (unit tests) and with a live probe of LFM3-Omni-2B Q4_K_M on llama-server b12359 (correct answers about a 1440x900 @2x screenshot at 2880, 1440 and 1024 px; about 660 prompt tokens and 0.7 to 1.2 s at 1024 px); the real capture with the permission granted and any hosted vision provider are not verified.
- `evals/run.py --vision` (assistant path): offers a stubbed `look_at_screen` (a fixed fake screen; nothing is captured or sent), with 11 cases in `evals/assistant_vision_cases.json` (5 screen questions, 6 that must not call it).
- Assistant mode long-term memory (#87, #8; `VAICE_ASSISTANT_MEMORY`, off by default, assistant mode only): three skills, `remember(note)`, `forget(about)` and `forget_everything`, keep short notes the user asks for ("remember that I park on level three") in `<VAICE_DATA_DIR>/memory.json` (mode `0600`, atomic write; in memory only when `VAICE_DATA_DIR` is empty) and put them at the end of the brain's system prompt in every later reply, behind a header that calls them facts, not instructions. Nothing is extracted in the background: only an explicit request stores a note. `remember` and `forget` run at once and name what they kept or removed (`remembered: ...`, `forgot: ...`, because a replayed call whose arguments were too long, or stored before they were replayed, has none); `forget_everything` is a `confirm` skill (`Shall I erase all 3 notes I keep?`, voice or the **Run** button) and `forget` needs at least 3 letters. A note is model-written text carried by every later prompt, so it is cleaned (one line, no control characters, chat markers, code fences or list markers), limited to 200 characters, and the store to 30 notes; a new `direct_only` flag on `Skill` makes `remember` refuse when another skill already ran in the same reply, so a file name or a command's output cannot become a note. A *Memory* panel under *Tool activity* lists the notes as escaped plain text; *New conversation* leaves them alone. Startup logs the number of notes and their location, never their text, and the remote-helper warning now says the notes are sent too. With memory off the skills do not exist and the file is not read; with memory on and no notes the brain's prompt differs from before only by the three extra tool definitions. New: `memory.py`, `conversation.write_json_atomically` (the conversation file now uses it too), `default_skills(memory=...)`. The notes are plain JSON, not encrypted.
- `evals/run.py`: the assistant path now offers the memory skills over a fresh in-memory store per run (the real `memory.json` is never read or written; a store with a file is refused), cases may carry `"notes"` (loaded into that store and put into the system prompt as the app does), a new `{"contains": "text"}` argument matcher for free text, `answer_has` also works on a case without a tool call (a recall from the notes), `--no-memory`, and 14 `memory-*` cases in `assistant_cases.json` (now 65, 25 must-not-call). Not measured at scale: only a smoke run of the new cases, then one full eval (63 cases x 5 on the local 2B, x 3 on a 24B helper) that found the two problems below.
- Memory notes are lasting facts, not words or reminders (full-eval findings): the 2B model called `remember({"note": "Goodbye"})` for "Goodbye." (5 of 5), and both the 2B (5 of 5) and the 24B helper (3 of 3) turned "Remind me to call mom tomorrow at nine." into `remember(...)` and answered "I've saved a reminder", which is false because nothing in vaice fires later. `clean_note` now refuses a note of fewer than 3 words ("there was nothing to remember") and a note bound to a moment (remind/reminder, tomorrow, tonight, today, setting a timer or alarm, "in 10 minutes", "on Friday", a clock time that is not a stated habit) with "I can't set reminders or timers; I can only keep lasting facts about you"; the same rules apply to notes loaded from the file (a refused one is skipped with the usual warning). The `remember` description says it is for lasting facts and not for reminders. New eval cases `memory-remember-birthday` and `memory-no-reminder-dentist`.
- Assistant mode: a final answer that is only bracket-style pseudo tool calls (`[open_file(path='old_report.docx')]`, `[find_files(name='resume*', path='/home')]`, seen with the helper model) is no longer spoken: `_spoken_text` drops it like other tool markup and the usual fallback applies (`Sorry, I couldn't work that out.`, or the skill's result after an approval), with the existing warning. Only an answer that is nothing but such calls; text that merely contains brackets is untouched.
- Assistant mode spoken progress (#87): when the answer has not started `VAICE_ASSISTANT_PROGRESS_SECONDS` (default 2.5, `0` = off) after the question was transcribed, the assistant says "One moment." and then "Still working." every 12 s until the answer starts, so a slow helper model or a long voice-approved command is not silence. A fast answer, an unheard question and a stopped reply get no filler; the filler is synthesized through `/tts` like any sentence, queued ahead of the answer (and of a confirmation question), and is not recorded in the turn or the history. A `/tts` failure while speaking it is a warning and the reply goes on. Counts as audio handed out, so a barge-in trims the recorded text slightly less than it otherwise would. On speakers the microphone may hear it as an interruption (#36): turn it off there. Not tried on speakers.
- Assistant mode helper model (#87): `VAICE_BRAIN_URL` points the brain step at any OpenAI-compatible chat-completions endpoint, a local server (LM Studio, Ollama) or a hosted API; vaice does not tell them apart. The value is the base URL OpenAI clients take, `/v1` included (vaice posts to `<base>/chat/completions`; a URL ending in `/chat/completions`, or holding credentials, a query or a fragment, exits at startup). `VAICE_BRAIN_MODEL` (sent as `model`; a helper URL without one warns), `VAICE_BRAIN_API_KEY` (a secret: only in the `Authorization` header, never logged, never in an error or the eval results) and `VAICE_BRAIN_TIMEOUT` (default 60 s). Unset = today's behaviour; ignored in chat mode with one warning. Only the brain moves: transcription and `/tts` stay on the local llama-server. The helper request holds `messages`, `tools` and `model` only (no `temperature`, no token cap: hosted models differ, and a cap cuts a reasoning model's answer short), and the assistant message sent back in later rounds holds only `role`, `content` and `tool_calls`, so `reasoning_content` (seen with LM Studio) is never replayed or spoken. Startup logs the helper's host and model and warns when the host is not local, listing what is sent (what you say, earlier turns, skill results such as file names, process names, the computer's name and shell output; never audio). A failing brain is now audible: `BrainError` (refused key, HTTP 429, timeout or connection error, other HTTP errors, an unusable reply) is spoken as a short fixed sentence through `/tts` and still shown as `(error: …)` in the chatbot; the 401/403 message never includes the response body, and after you approved an action a failed follow-up speaks the skill's result instead. A reply cut off at the token limit with nothing said logs a warning. `ChatBrain` now takes the full endpoint URL (`ChatBrain.local(url, timeout)` and `ChatBrain.helper(base_url, ...)` build it); the local brain still sends `temperature: 0` and `max_tokens: 300`. This also changes the local brain: its failures are `BrainError` (a `RuntimeError`) and are spoken, and the message it sends back no longer carries keys other than `role`, `content` and `tool_calls`.
- `evals/run.py --brain-url` / `--brain-model` (assistant path; default `VAICE_BRAIN_URL` / `VAICE_BRAIN_MODEL`; the key only from `VAICE_BRAIN_API_KEY`, never a flag and never in the results, which record the brain's host and model). Two optional case expectations scored apart from the call verdict: `answer_has` (strings that must appear in the final answer) and `command_matches` / `command_not` (regular expressions on the `run_shell` command); the summary prints `answer faithful k/N` and `command ok k/N` and the per-case table gets a column each. Expectations added to the assistant and shell cases. The `system_info` stub's hostname is now `Example-MacBook`.
- Assistant mode (`VAICE_MODE=assistant`, opt-in; the default `chat` mode is unchanged): the reply is built from separate steps instead of one speech-to-speech session. The audio is transcribed (realtime `transcription` session), a brain (`POST /v1/chat/completions`, temperature 0, at most three rounds) answers or asks for one of vaice's own skills (`disk_space`, `battery_status`, `system_info`, `top_processes`, `find_files`, and the actions below; macOS only, run in vaice with its permissions, llama-server's `--tools` unused), and the answer is cleaned for speech (`voice.speakable`), split into sentences and spoken through llama-server's streamed `POST /tts`. New settings `VAICE_MODE`, `VAICE_ASSISTANT_PROMPT` and `VAICE_VOICE` (`female`/`male`); new modules `brain.py`, `skills.py`, `voice.py` and `responders/assistant.py`. On llama-server b12359 first audio is 0.6–1.7 s. Earlier skill results are carried into later turns' prompts (assistant mode only, as real tool exchanges, each capped at 300 characters), so a follow-up such as "and how much memory does it have?" is answered from the real result instead of from the model's head. `top_processes` speaks cleaned process names: a trailing "(Renderer)" is dropped, helpers count with their app and reverse-DNS names are shortened to their last part, then the names are summed and sorted; the raw rows stay in the Tool activity detail. New: `Conversation.history(before, tools=False)` and an optional `tool_history` attribute on `Responder`.
- Assistant mode actions: `open_app`, `quit_app`, `set_volume` (a `level`), `volume_up` and `volume_down` (10 points, no arguments) and `mute_sound`, all run by vaice with argv lists and no shell. Each result names what it did (`opened Safari`, `volume set to 40 percent`), because a replayed call whose arguments were too long, or stored before they were replayed, has none. A skill that cannot be undone (`quit_app`) is a `confirm` skill: it does not run when the model asks; vaice speaks a question it builds itself from the validated arguments (`Shall I quit Safari?`) and holds the request in `Confirmations` (`confirm.py`), one at a time. A spoken answer counts only as a whole utterance: `yes` runs the stored call (the model gets one tool-less call to say how it went), `no` cancels, anything else drops the request and is an ordinary question. The request cannot be answered before all of its question's audio was handed out, expires 60 s after that, and is dropped by *New conversation*. A panel above *Tool activity* shows the question and the exact call with **Run** and **Cancel** buttons bound to the request's id, so a stale panel cannot approve a newer request. `quit_app` may trigger macOS's Automation permission prompt on first use. There is no web search skill: it made the 2B model search for questions it could answer itself (eval 185/245 against 170/175 without it); it is planned to return with the helper model. The brain's final answer is also stripped of raw `<tool_call>` markup (as in chat mode) before it is spoken, and an answer that is only markup becomes "Sorry, I couldn't work that out."
- Assistant mode shell commands (`VAICE_ASSISTANT_SHELL`, off by default): a `run_shell(command)` skill behind the confirmation step. Nothing runs when the model asks. A command that is one program from a short fixed list that only lists or reports (`ls df du date uptime whoami pwd sw_vers hostname uname`, with argument rules) and holds no shell syntax at all can be approved by voice or click and runs as an argument list with no shell; every other command runs through `/bin/zsh -c` and only after the **Run** button (a spoken yes is answered with `This one needs the Run button on the screen.` and the request stays pending). `sudo` is refused before any question. The question is a fixed sentence built by vaice (only the program's name, never the arguments, is spoken); the panel shows the command itself and says when only the button can approve it. Commands run in the home folder in their own process group with no input, are stopped after 30 seconds, on barge-in or app stop (spoken approval), on *New conversation* or app stop (click approval), keep at most 20,000 characters of output, and the model gets a one-line outcome plus the first 600 characters of output (`(more on screen)` when cut). New: `shell.py`, `Skill.run_stoppable`, `Skills.run(..., stop)`, `Skill.ask` may return a `Question`, `Question.voice` / `Pending.voice`. Commands run with vaice's own permissions; vaice logs a warning at startup when the setting is on.
- `evals/run.py --shell` (assistant path): offers a stubbed `run_shell` (it asks, nothing is run), with 12 cases in `evals/assistant_shell_cases.json` (6 spoken command requests, 4 tempting must-not-call ones, 2 other skills).
- `evals/run.py --paths assistant`: a third eval path for assistant mode (transcribe, then the real brain and skill loop with stub skills; nothing is executed), with its own 51 cases in `evals/assistant_cases.json` (18 must-not-call) and a `--cases-file` option. It is not in the default `--paths`.
- `evals/`: a live eval, run by hand against a real `llama-server`, that measures how reliably spoken commands turn into the right tool call (`python evals/run.py`). It runs about 33 spoken cases (macOS `say`, or real-mic recordings in `evals/recordings/`) with repeats on two paths: the app's interleaved `/v1/realtime` path with stub tools, and transcribe-then-route through `/v1/chat/completions`. The report gives correct / missed / overcall / wrong-args / duplicate / error counts, time to first audio or decision, and a per-case `k/N` table; the results JSON keeps every raw run. Only its scoring logic is unit-tested (`tests/test_eval_scoring.py`); CI does not run it.
- `vaice up`: one command that makes sure a `llama-server` is running, then starts the UI and opens the browser. A server that already answers `/health` (200, or 503 while loading) at `VAICE_LLAMACPP_URL` is reused and never stopped; otherwise, for a local URL, `vaice up` finds `llama-server` on `PATH` (it never installs it; a missing binary or a build older than 11960 exits with the `brew install` / `brew upgrade` command), starts `llama-server -hf <model> --temp 0 --host <host> --port <port>` plus extra arguments, waits for `/health` (progress every 10 s; an early exit of the child, the timeout or Ctrl+C ends the wait with a clear message), and stops the child (terminate, then kill after 5 s) when the app ends for any reason. Its output is appended to `<VAICE_DATA_DIR>/llama-server.log`. New settings: `VAICE_LLAMACPP_MODEL`, `VAICE_LLAMACPP_SERVER_ARGS` and `VAICE_LLAMACPP_START_TIMEOUT`. Plain `vaice` is unchanged. The README quickstart now starts with `vaice up`; running `llama-server` yourself stays documented as the manual alternative.
- `VAICE_DATA_DIR=""` keeps the conversation in memory only: nothing is read from or written to disk, and the history disappears when the app stops. Documented together with the privacy facts (the `0600` mode of `conversation.json`, the `0755` mode of `~/.vaice`, the indefinite retention, and that everything relevant leaves the machine only toward the local `llama-server`).
- A `/v1/realtime` WebSocket probe in `check_server`: after the health and model checks pass, the startup check opens the realtime endpoint once (2 s timeout) and closes it. A server whose HTTP endpoints answer but which does not route `/v1/realtime` (an older llama.cpp, a proxy) now fails at startup with an actionable message instead of at the first question after a 120 s stall. A rejected handshake (e.g. 404) raises — it is permanent; a connection-level failure only warns, like the health check.
- `VAICE_LLAMACPP_TOOLS`: voice access to llama-server's built-in tools over `/v1/realtime`. Tool definitions are fetched from the server's `GET /tools` at startup, declared in each `session.update` (flat Responses API format, `tool_choice: "required"`), a spoken question's `function_call` events are executed through the server's `POST /tools`, and the model speaks the result. Off by default; `builtin` takes every tool the server advertises. Validated live against llama-server b12359 with LFM3-Audio: the call rate depends on the prompt (default prompt ≈ 1 call in 6 runs; a "use the available tools" prompt 4 in 4), `auto` never calls, 3+ tools hallucinate, a tool round is capped at 2, and executor failures are spoken, not raised.
- Tool results are compacted before they are fed back (`_speech_friendly`: JSON → short `key: value` pairs, values truncated at 200 chars, the whole output capped at 800 chars) — the voice model reads the fed-back result aloud (a 2B-model limitation; prompt lines forbidding it have no measurable effect), so the compaction keeps the spoken dictation short while the first sentence answers. The caps are configurable with `VAICE_LLAMACPP_TOOL_VALUE_CHARS` and `VAICE_LLAMACPP_TOOL_OUTPUT_CHARS`; the old 40/120 defaults cut a `get_info` timestamp off before the model could speak it.
- A startup warning names any advertised tool the server marks `permissions.write` (`exec_shell_command`, `write_file`, `edit_file`): they run with the server's own permissions, so the server's `--tools` should be a read-only subset for a voice demo.
- The UI shows tool calls and their results in a collapsed *Tool activity* panel under the chatbot (the last 10, with arguments cut); the conversation itself stays speech-only.
- Every reply's instructions now carry the current local date and time (built per reply; the model has no clock of its own). A bare `Current date and time: …` line was treated as inert text — the model echoed it and still answered "I don't have access" (live A/B, 6 runs) — so the line is phrased as something the model knows and is told to use; that wording answered with the real time 6/6.
- A reply loop breaker: under `--temp 0` the model sometimes cannot stop after answering and repeats the same short block to the token cap (seconds of junk audio). If the same 1–4-line block repeats three times back-to-back (compared with case and punctuation ignored), the reply is cut there: the repeated tail is dropped from the transcript and the realtime session is closed, freeing the server slot.

### Changed
- Around a tool round, only the final round's text is recorded: whatever the model says before a tool result (the working-out-loud preamble) is spoken all the same, but it is not written to the conversation — the text and the spoken-part share restart at each tool-round boundary, so a wrong first pass cannot reinforce itself in history.
- Tool-call follow-ups no longer inherit the session's `tool_choice: "required"`: after a tool result the next response is requested with `auto`, and after the second round a final answer is forced with `none` (a call in that forced round is ignored). The first response still uses `required`.
- The tool-result compaction defaults are raised from 40/120 to 200/800 characters, so answer-bearing data (an OS build timestamp, the end of a file) survives the round trip.
- `VAICE_LLAMACPP_TOOLS` is now on/off (`builtin` = every tool the server advertises, unset = off): the tool set is the server operator's decision (`llama-server --tools`), which is also what `POST /tools` executes (an unadvertised tool is refused by the server, live-verified 404) — the client-side subset and refusal guard were a second source of truth and are removed. A comma-separated value now exits with a message pointing at the server's `--tools`.

### Fixed
- The user transcript and the end of every reply were reported 1 s late: `llama-server` does not complete the WebSocket close handshake, so closing the session waited out the 1 s close timeout before the transcript was handed over or the reply was marked finished. The close now runs on a daemon thread of its own (the close frame is still sent at once, so the server frees the slot). Measured on b12359: transcript after 0.16 s instead of 1.17 s; the reply ends with its last audio frame instead of 1.00 s later (#90).
- A tool round could not end in an answer: the follow-up response inherited `tool_choice: "required"`, so the model called again, repeated the raw result in its text, and could loop until the token cap (live: the same sentence repeated to 1024 tokens, 62.7 s of audio).
- A reply that hit the 2-round tool cap now gets a forced final answer instead of stopping after the last call.
- The recorded reply text is cleaned of model markup: `<tool_call>…</tool_call>` blocks, `<think>`/`<thinking>` tags (including orphan `</think` fragments), stray `<|…|>` control tokens and `<answer>` delimiters are dropped from the streamed text before it is recorded or shown, across deltas (the sanitizer holds back partial tags split across chunks).
- The *Tool activity* panel and the persisted tool events now cap each result at 800 characters with an explicit `... (truncated)` marker, and old events are bounded the same way at render time, so a long file does not bloat the UI or `conversation.json`.
- A router-style `/props` (no `params`) or a failed `/props` fetch is no longer silent: `vaice` now logs a distinct hint ("could not verify the server's temperature … start llama-server with `--temp 0`"), so a missing temperature warning cannot be mistaken for greedy decoding being configured.
- A transcription session whose server never answers the websocket upgrade no longer blocks its thread for the whole `VAICE_LLAMACPP_TIMEOUT` (120 s): the handshake now uses the short startup-check timeout, as a transcription is best-effort and degrades to an empty transcript anyway.
- Test coverage for the riskiest paths that were untested: the `app.py` tools-fetch failure / startup warning block and the `KeyboardInterrupt` exit path (including `request_stop()` at exit), non-JSON server messages and a malformed `session.created`, the `_Stopped` control-flow branches in `expect`/`rates`/`update`/`_transcribe_into`, the fastrtc-upgrade guards in `InterruptSafeReplyOnPause` (it now fails loudly at construction when `generator`/`event` are gone), and the negative-VAD configuration error. The triplicated "fresh thread per `next()`" test harness is now one shared helper in `tests/threads.py`.
- A tool call can no longer block the session thread for the whole 120 s timeout while ignoring a stop: the default executor now runs the `POST /tools` on a daemon thread and stops waiting when the reply's stop signal fires or the configured timeout passes, so a stopped reply gives up within about a second — without destroying the underlying HTTP request (a healthy slow tool runs to completion). The session also no longer asks the model to continue after the tool results when the stop already fired.
- The "reply had no audio" warning no longer fires for a tool-call response, which has no audio by design.
- `read_file` (and any tool with parameters) never received its arguments: the executor sent the model's JSON string as `arguments`, while `POST /tools` reads the parameters object from `params`. `get_info` worked only because it takes none; `read_file` got `key 'path' not found`. The arguments are now parsed and sent as `params`.
- A plain-text `read_file` result lost its last word when the per-value compaction cap (200) cut a 210-character file; a `plain_text_response` payload is now bounded by the whole-output cap (800) instead.
- Docs honesty: the echo troubleshooting entry and the "Language & voice" note blamed llama-server's `--tts-lang`/`--tts-voice` for making LFM3-Audio parrot user speech, citing a repro. A controlled re-test on the same build (b12359, `Q8_0 --temp 0`) did not reproduce the parroting — with the flags, with per-session `audio.output.language`/`audio.output.voice`, or with the exact injected prompt line on a flagless server, across clean TTS and noisy mic inputs (`tasks/repro_tts_lang.py`). The flags are no longer presented as a proven echo cause; the advice to omit them stands (English-only voice model, the pin buys nothing). History clearing and `--temp 0` remain the echo fixes.
